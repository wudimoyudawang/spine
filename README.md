# 书脊 · Spine

**个人计划中枢** —— 一个本地优先（local-first）的个人管理系统。

习惯打卡、待办、长短期计划、记账、热量与体重、随心记、复盘，全部收在一处。
**未登录也能完整使用全部功能**，登录只是为了多端同步。

## 为什么做这个

起因不是「某个功能不够强」，而是**信息散在各处**：备忘录记事、日历排时间、Excel 记计划，
来回切换、容易漏。

所以这个项目的第一原则是：

> **任何东西 3 秒内能记下来；今天该做什么，一眼看到。**

这不是一句口号，它是一条验收标准：新增任何功能，「记一笔」的中位操作步数超过 3 步就算不合格。
细节见 [`docs/开工方案.md`](docs/开工方案.md) 第 9 节。

## 核心设计决策

这五条决定了整个数据结构和交互，后面所有功能都建在它们之上。

| # | 决策 | 含义 |
|---|---|---|
| D1 | **统一事项模型** | 所有事都是同一种记录 `Item`，靠四项标签区分：**形态**（习惯/待办/计划）、**领域**（健身/学习/工作/个人…）、**跨度**（短期/长期）、**状态** |
| D2 | **领域是主组织轴** | 健身页、学习页各自**混装**该领域全部内容，不需要在页面之间跳转 |
| D3 | **形态是交互轴，不进导航** | 习惯行是打卡按钮，待办行是勾选框，计划行是进度条 —— 它决定「怎么完成」，不决定「在哪儿」 |
| D4 | **跨度是属性，不是页面** | 「短期 / 长期」只影响怎么排期和提醒。开成两个页面会让你有大量事项纠结该放哪边 |
| D5 | **Local-first** | 本地存储是主体，云端是可选增强。核心层永远不依赖网络、不依赖账号、不依赖任何外部服务 |

两条由此推出的推论，值得单独说：

- **「记账 / 热量 / 体重 / 打卡」不是四个功能，是同一种东西** —— 带数值的按时间记录。
  它们在数据库里共用一张 `log` 表，靠 `kind` 和「记录项定义」区分输入界面。
  所以你将来想加「喝水量」「睡眠时长」「阅读页数」「模拟考试分数」，**不用改表结构**。
- **领域是用户自己长的，不是写死的四个。** 每个领域天生带三样通用容器（习惯 / 待办 / 长期目标），
  你可以自由新建、改名、删除、置顶到顶部快捷。领域里还能自己定义「记录项」——
  纯文字（记过程和感受）或数值（看趋势），两种方式，名称和单位你自己填。

## 界面结构

一级导航固定五项，**长度不随功能增长**：

（手机上它们落在**底部 Tab 栏**：「记账」和「设置」收进右侧的「更多」抽屉；
记东西的入口是底部中间那颗「记一笔」，点开把速记框展开成底部弹层。）

| 入口 | 职责 |
|---|---|
| **今日** | 跨领域聚合：逾期置顶 → 今天到期 → 今天该打卡的 → 长期计划进度。顶部是唯一的速记框 |
| **收集** | 收件箱。只解决「先记下来别丢」，分类以后再补 |
| **随心记** | 零字段文本框，无统计、无红点、无连续天数。默认**不进**任何聚合与复盘 |
| **空间** | 两层：**领域**（健身/学习/工作/个人 + 你自己建的）+「记账」入口 |
| **复盘** | 周 / 月 / 自定义周期，结论可以回写成新的待办 |

下面还有一段动态区：**你置顶的领域**。左侧那五项是固定的，动态区完全由你自己勾 ——
这就是「入口不会越排越多、最后找不到东西」的实现方式。

## 技术栈

前三层在**第 1 步**就要定，后三层第 5 步才做。所以第一阶段你一行后端代码都不用写。

| 层 | 选型 | 状态 |
|---|---|---|
| 前端 | React + TypeScript + Vite + Tailwind | 计划中 |
| 前端存储 | IndexedDB（Dexie），通过 `StorageAdapter` 抽象层访问（原型现用 localStorage 顶着，接口就是 `snapshot()` / `restore()` 两个函数） | 原型已落本机 · 正式版待做 |
| 类型共享 | Pydantic → OpenAPI → 生成的 TS 类型 | 计划中 |
| 后端 | Python + FastAPI + SQLModel | 第 5 步 |
| 数据库 | SQLite 单文件 | 第 5 步 |
| 部署 | Docker Compose 单容器 + Caddy | 第 5 步 |

上表是 Web / PWA 形态的选型。**手机上先走 PWA**（加到主屏即可用，不用打包、
不用签名），确认需要硬件能力（蓝牙心率带之类）时再用 Capacitor 打包成真 App，
同一份页面代码不用改。详见 [`docs/平台形态与系统能力.md`](docs/平台形态与系统能力.md)。

**存储层必须走抽象接口**（`StorageAdapter`）。原因见
[`docs/平台形态与系统能力.md`](docs/平台形态与系统能力.md)：iOS 上浏览器存储可能被系统回收，
将来要换成 SQLite 时，只应该改这一层。

## 路线

五步，**每一步结束时都必须能真的打开来用**。
不按「先做完功能再能用」的顺序施工 —— 那样你会长期对着一个跑不起来的半成品，
而且任何一处设计错了都要到最后才发现。

| 步 | 目标 | 做完后能干什么 |
|---|---|---|
| **1** | 能记下来 | 仓库骨架 + 存储层 + 一个速记框 + 列表。随手写一句就能存住并落对地方 |
| **2** | 能看清今天 | 今日视图 + 领域 Hub + 三种交互 + 领域可自定义 + 规则编辑器 |
| **3** | 能记住细节 | 记录流 + 领域记录项自定义 + 记账 + 随心记 + 一键导出 |
| **4** | 能回头看看 | 复盘 + 体重 + 热量 |
| **5** | 能给朋友用 | Docker 打包 + 后端 + 账号 + 增量同步 + 开源发布 |

**第 5 步之前完全不碰服务器。** 先做后端，等于在没有任何真实使用数据的情况下设计同步协议 ——
这是这个项目里最贵的错误。

## 贡献

欢迎 Issue 和 PR。但请先读 [`CONTRIBUTING.md`](CONTRIBUTING.md) ——
里面列了一串「看起来像缺陷、其实是刻意设计」的行为，能省下双方不少时间。

三条硬约束，不接受折中：

1. 核心层**不许**依赖网络、账号或任何外部服务。
2. 核心功能**不许**依赖 AI。AI 只能长在可一键关闭的扩展层。
3. 新功能必须能被「今日视图」或「领域页」吸收。两个都进不去的，大概率不该进这个应用。
