# 与两个 Agent 项目的技术协同

**日期**：2026-09-18  **面向**：宇
**性质**：对《开工方案》的修正与补充。**不改变任何产品需求**，只改技术选型，并在计划中枢里划出「练习区」。

---

## 0. 一句话结论

**把后端从 Node 换成 Python。** 这一改，你的计划软件就从「和学 agent 抢时间的项目」变成「学 agent 的练习场」——成本为零，因为**第 5 步之前你根本不碰后端**。

而且这不是自欺欺人：下面那三个练习点（结构化输出、向量检索、MCP Server）都是计划软件**本来就要做**的功能。你不是在给自己加作业，是在把作业换个做法。

---

## 1. 我修正了什么

《开工方案》第 2 节的技术栈表，两行作废：

| 层 | 原方案（作废） | 修正为 | 为什么 |
|---|---|---|---|
| 后端 | Node.js + Fastify + TypeScript | **Python 3.12+ / FastAPI + Pydantic v2 + SQLModel** | Pydantic 就是 Function Calling 的 schema 来源，FastAPI 就是 MCP Server 的宿主。你学的和用的变成同一套东西 |
| 前后端共享 | `packages/shared` 手写 TS + zod | **Pydantic model（唯一事实来源）→ FastAPI 自带 OpenAPI → `openapi-typescript` 生成前端 TS 类型** | 类型仍然只写一遍，但写的是 Python 那一遍。生成物是产物，不是源码 |
| 数据访问 | better-sqlite3 | **SQLModel / SQLAlchemy 2.x + SQLite** | 同一个 SQLite，换驱动 |
| 向量检索 | （原方案没有） | **sqlite-vec 扩展**，和主库同一个 `.db` 文件 | 零额外部署。**不要为练手引入 Milvus 容器**，那会让 NAS 部署复杂化 |
| 前端 | React + TS + Vite | **不变** | 前端没有 Python 替代品，这个选择本来就是对的 |
| 数据库 | SQLite | **不变** | 判断仍然成立 |
| 部署 | Docker Compose 单容器 | **不变** | FastAPI 一样能托管前端静态文件 |

**为什么不选 Go / 继续用 Node**：原方案说「一个人维护两套语言不划算」是对的，但前提是你不需要 Python。现在你需要 —— 你的两个目标项目（知识图谱、多 Agent）都是 Python 生态。**让计划软件成为 Python 的第一段肌肉记忆，是这份协同里收益最高的一步。**

**代价（我要如实说）**：

- 单容器镜像会从约 60MB 涨到约 200MB。对你自用的 NAS 完全无所谓。
- FastAPI 的类型安全弱于 TS 的端到端推导。用 OpenAPI 生成能补上大半，但不是零损耗。
- 少一个「前后端同语言、改一个文件两边都变」的便利。换来的是整个 Python agent 生态。

**这些代价我认为值得。** 如果不值得，就退回 Node，那三个练习点改用「调 Python 小服务」的方式做 —— 但那样反而更复杂。

## 2. 三条硬边界（「不影响项目」的全部含义）

AI 功能放进一个「随时能不要」的层里，三条规矩缺一不可：

1. **核心层不许有 LLM 调用。** 记一笔、今日视图、领域页、记录流、复盘汇总 —— 这些断网、无 API key、模型宕机时都必须照常工作。
2. **LLM 只出草稿，绝不写库。** AI 解析出「明天下午 3 点 / 交周报 / 工作」之后，是**填进表单让你确认**，不是直接落库。这叫人在回路（human-in-the-loop），恰好也是你 agent 项目里最该学的一课。
3. **增强层可一键关闭。** 关了之后软件功能不减一分。这条同时保护开源后的其他人 —— 他们不一定想填 API key。

再加上一条工程纪律：**不为学习引入运行依赖。** 所以向量检索用 sqlite-vec（一个 SQLite 扩展、同库、无服务），而不是起一个 Milvus 容器。想练 Milvus，去知识图谱项目练 —— 那里它才是刚需，而不是玩具。

## 3. 四个练习点

每一步只在上一步的产物上工作，且都能独立跳过。

### 练习点 ① 结构化输出 / Function Calling
- **落在哪**：第 2 步（今日视图）之后的增强层。「速记」输入框多一个「AI 解析」按钮。
- **做什么**：输入「明天下午3点 交周报 #工作」→ 解析出 `{due_at, title, domain}` → **填进表单**。
- **学到**：工具 schema 设计、structured output 的字段约束、解析失败与校验、few-shot 示例、中文时间表达。
- **对应你的课程**：SmartVoyage 2.1 Function Call。
- **约束**：解析失败必须能无声退回手填。**不能因为 AI 解析失败就记不下来。**

### 练习点 ② Embedding + 向量检索 / RAG
- **落在哪**：第 4 步之后的增强层。随心记页面加搜索框。
- **做什么**：「翻我上个月写过的关于 X 的东西」，按语义而不是关键词召回。
- **学到**：切分策略、embedding 模型选型（中文场景、本地 vs API）、向量索引与距离度量、**混合检索**（BM25 + 向量，纯向量搜中文短文本效果常常不够）、召回评估。
- **技术选型**：`sqlite-vec`。理由：和业务数据同库，不用同步、不用多一个服务。代价是没有 ANN 索引（暴力检索），**约 10 万条向量以内够用** —— 你的随心记一辈子也到不了这个量级。将来真需要，可平滑换 LanceDB 或 Milvus Lite（API 兼容 Milvus 正式版）。
- **约束**：这是「搜索」，不是「对话」。不做聊天框 —— 那是另一个项目的事。

### 练习点 ③ MCP Server
- **落在哪**：第 4 步之后。**性价比最高的一步。**
- **做什么**：把计划中枢的能力暴露成 MCP Server。之后你在任意 MCP 客户端里就能问「我今天有什么待办」「帮我记一笔午餐 35 元」。
- **学到**：MCP 三原语（tools / resources / prompts）、stdio 与 Streamable HTTP 两种传输、MCP Inspector 调试、**为什么 docstring 就是 API**（MCP 会把函数签名和 docstring 当工具 schema 发给模型，写得含糊模型就会在错误的时机调用）。
- **对应你的课程**：SmartVoyage 2.2 MCP 协议 + 3.3 实现 MCP 服务。
- **为什么值**：你的后端已经有 REST API 了，MCP Server 只是薄薄一层封装。而且**你会真的用它** —— 这是你唯一一个「有真实用户的 agent 练习」。
- **必踩的坑（先记住，省你两小时）**：Python 里叫 FastMCP 的有两个包，且写法不兼容 —— 官方 SDK 的 `from mcp.server.fastmcp import FastMCP` 用 `@mcp.tool()`（带括号），Prefect 维护的独立版 `from fastmcp import FastMCP` 用 `@mcp.tool`（不带括号）。抄错来源的代码片段会静默失效。**建议先用官方 SDK**，它和协议规范对齐、依赖最少。

### 练习点 ④ 单 Agent 工作流
- **落在哪**：第 4 步的复盘页面。「生成一段总结文字」。
- **学到**：单次 LLM 调用 → 带工具循环 → 有限状态机。这三级是同一个东西的不同复杂度，**先做第一级**。
- **约束**：**不要在这里做多 agent。** 复盘是一次 LLM 调用就能解决的事。多 agent 在这里只有坏处（更慢、更难调、失败模式更多）。

## 4. 你的两个目标项目：能力清单与练习地

### 项目 A：知识库 + 知识图谱

| 环节 | 需要的能力 | 计划中枢能练到吗 |
|---|---|---|
| 文档摄取 | Docling / markitdown / PyMuPDF | ✗ 到目标项目练 |
| 切分 | 切分策略（**最容易做错的一步**） | △ 概念相同，随心记是短文本，规模不同 |
| Embedding | 模型选型、维度、中文效果 | ✓ 完全一致 |
| 向量库 | Milvus | △ 计划中枢用 sqlite-vec；Milvus 到目标项目练 |
| 实体/关系抽取 | 结构化输出 + schema 设计 | ✓✓ **练习点 ① 就是这个** |
| 图存储 | Neo4j / NebulaGraph / NetworkX | ✗ 到目标项目练 |
| 检索 | GraphRAG、混合检索、rerank | △ 混合检索能练，图检索不能 |
| 评估 | 召回率、忠实度 | ✓ 练习点 ② 的「召回评估」是同一个技能 |

**结论**：计划中枢能替你练掉「Embedding + 抽取 + 检索 + 评估」，**练不掉的是图这一层**。图数据库本身不难，难的是图 schema 设计 —— 那个只能在真实语料上练。

### 项目 B：多 Agent 协同

按你 SmartVoyage 的目录倒推：

| 课程章节 | 计划中枢能练到吗 |
|---|---|
| 2.1 Function Call | ✓✓ 练习点 ① |
| 2.2 MCP 协议 | ✓✓ 练习点 ③ |
| 2.3 Agent 智能体 | △ 练习点 ④（只到单 agent） |
| 2.4 A2A 协议 | ✗ 到目标项目练 |
| 核心协调器（chat_service.py） | △ 概念上就是练习点 ④ 的状态机 |
| memory.py（偏好 / 历史 / 短期对话） | ✗ 计划中枢没有对话上下文，别硬塞 |
| 部署（Docker） | ✓✓ 计划中枢的 Docker 完全一致 |
| **评估 / 可观测性** | **✗ 你课程目录里没有，但生产必须有** |

**结论**：计划中枢能练掉你课程里 **2.1、2.2 两章 + 部署**，也就是「工具与协议」这一整块。**A2A 和 memory 到目标项目练** —— 它们需要多进程、多角色，计划中枢提供不了这个场景。

### 我注意到你课程里缺的两课

这两样在 SmartVoyage 的目录里没有，但生产环境必须有：

1. **可观测性** —— Langfuse / LangSmith 一类。Agent 的行为是概率性的，没有 trace 你无法回答「它为什么这次调用了错误的工具」。这是 agent 开发里最容易跳过、代价最大的一课。
2. **评估** —— 你怎么知道改了 prompt 之后 agent 变好了而不是变差了？没有评估集，你只能凭感觉，而感觉在概率系统上非常不可靠。

**这两个建议放回到你两个目标项目里做**，计划中枢规模太小，练不出手感。

## 5. 学习顺序与理由

**① 结构化输出 → ② 向量检索 → ③ MCP Server → ④ 单 Agent 工作流 →（到目标项目）多 Agent / A2A**

这个顺序不是按难度排的，是按**可迁移性**排的：

- **①②③ 是可迁移的基础能力**。任何 agent 项目都要用，且它们在计划中枢里都以「真功能」的形式存在，你练完就有能用的东西。
- **④ 是第一个架构决策**。做对了省事，做错了返工。
- **⑤ 多 Agent 是架构决策，不是技能**。而且**大多数场景不需要它**。行业的实践共识（Alice Labs 基于 100+ 实现的总结）是：「crew 之间用 A2A，crew 内部用 agents-as-tools —— **不要在同一个进程里为 agent 之间加 HTTP 跳转**。」你先不用急着上多 agent，等你真的有一个「A 做完交给 B 再交给 C」的任务再说。

### 一个必须知道的行业事实：你学的东西不会过时

- **MCP** 2024 年 11 月由 Anthropic 提出，现在归 Linux Foundation 治理，Python 是官方 SDK 语言之一。**2026 年中生态已到千万级月下载量**。
- **A2A** 2025 年 4 月由 Google 发布，2026 年 3 月发布 **v1.0 稳定版**，2026 年 4 月（一周年）时已有 **150+ 组织**支持、**22,000+ GitHub stars**、**5 种语言的官方 SDK**，2026 年 8 月正式成为 Linux Foundation 的 AAIF 托管项目。IBM 的竞争协议 ACP 已合并进 A2A。

**两个协议互补，不是竞争**：MCP 管「agent 到工具」，A2A 管「agent 到 agent」。业界已从「MCP vs A2A」的争论转向「两个都用」的双栈架构。你按这个顺序学，方向是对的。

### 学习资源（挑一个就够，别囤）

| 主题 | 推荐 |
|---|---|
| Agent 理论基础 | Lilian Weng《LLM Powered Autonomous Agents》（你课程 2.3 已引用） |
| Agent 工程实践 | Anthropic《Building Effective Agents》—— 讲清「什么时候**不该**用 agent」 |
| MCP | 官方 spec + 官方 Python SDK 文档（`py.sdk.modelcontextprotocol.io`） |
| A2A | a2a-protocol.org 的 spec + DeepLearning.AI 那门 A2A 短课 |
| 向量检索 | sqlite-vec 文档（很薄，两小时能读完）+ Milvus 文档的「索引类型」章节 |

## 6. 关于你那两份飞书文档

**SmartVoyage V7.5** 我读到了完整目录：4 个理论章节（Function Call / MCP / Agent / A2A）+ 8 个实现章节（架构图、MCP 服务、A2A Server、核心入口、Streamlit 控制台、Docker）。技术栈是 A2A + MCP + MySQL + Milvus + Streamlit + Docker，`chat_service.py` 做中心协调器，`memory.py` 管记忆。

**这份课程结构本身是扎实的** —— 四章正好是四个层次，且每章都配了实现。你缺的不是又一份教程，**是一个你能持续使用的真实项目**去把 2.2 和 2.3 落地。这正是计划中枢能补的位。

**草本通中医药知识图谱** 我只取到了目录标题，正文没读到（可能是权限或渲染方式）。如果你方便，把这几处贴给我，我能把学习路径对齐得更准：

## 7. 修正后的施工顺序

原 5 步不变，增强层的东西挂靠在对应步骤后面，**且每一条都可以单独跳过**：

| 步 | 目标 | 做完后你能干什么 | 挂靠的练习点 |
|---|---|---|---|
| **1** | 能记下来 | 仓库骨架 + 共享类型 + IndexedDB + 全局速记框 + 列表 | — |
| **2** | 能看清今天 | 今日视图 + 领域 Hub + 三种交互 | **① 结构化输出**（速记解析，可跳过） |
| **3** | 能记住细节 | `log` 记录流 + 记账 + 随心记 + 一键导出 | — |
| **4** | 能回头看看 | 复盘 + 体重 + 热量 + 健身属性包 + 语录卡片 | **② 向量检索**（随心记搜索）<br>**④ 单 Agent**（复盘配文） |
| **5** | 能给朋友用 | Docker + 后端 + 邀请码 + 增量同步 + 开源 | **③ MCP Server**（后端做好后顺手封一层） |

**注意 ③ 的位置**：MCP Server 要求后端存在，所以它只能在第 5 步之后。这是唯一一个受依赖顺序限制的练习点。

---

## 8. 一句话总结

**你不需要为学 agent 额外安排时间。** 把后端换成 Python，后面三步每步顺手做一件事，你就在用真实项目把 Function Calling、Embedding/RAG、MCP 三块练完 —— 而这三块正好是你两个目标项目里**最通用、最不会过时**的部分。

多 Agent 和 A2A 我没有替你找练习场景，因为**它们在你的计划软件里是纯负债**。到你的多 Agent 协同项目里再练，那里它们才是主角。
