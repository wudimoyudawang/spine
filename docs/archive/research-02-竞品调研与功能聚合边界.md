# 竞品调研与功能聚合边界

> **项目**：个人计划中枢（宇，第一阶段自用，后期部署于自建 NAS）
> **作者**：竞析（Compa）· 竞品分析师
> **日期**：2026-09-18
> **调研方式**：WebSearch / WebFetch 实时检索（所有结论标注来源与新鲜度，未验证处明确说明）
> **信息新鲜度说明**：本文所引事实集中在 2025-12 ~ 2026-09 的公开信息。产品功能与定价变动频繁，落地前请以官网为准。用户口碑类信息来自第三方评测、社区帖与投诉平台，**属主观样本，不构成统计结论**，仅用于识别「差评集中点」这一模式。

## 0. 一句话结论（给主理人先看）

1. **功能聚合的边界 =「同一个决策闭环内的模块才聚合，跨闭环的一律外包」**。健身页（摄入+消耗+体重）是闭环，记账是独立闭环，日记是独立闭环。三个模块可以住在同一个 App 里，但**必须是三套独立的数据模型 + 三个独立入口**，绝不能塞进「统一事项模型」。
2. **热量录入的最低摩擦范式 =「一句话语义 + 复用上次 + 拍照兜底」三者叠加**，而不是任何单一方案。其中「一句话」是北极星，拍照是兜底不是主线——所有评测都指出拍照识别份量误差 30-50%。
3. **记账的最低摩擦范式 =「通知栏/短信自动抓取 + 一键确认」，手动记账必须 ≤2 步（金额→分类）**。「三步记账」是上界不是目标。
4. **本地优先对标结论：宇的产品不该对标 Obsidian（纯文件、无结构化）也不该对标 Actual Budget（纯单模块）**，而应对标 **Super Productivity 的架构（本地优先 + BYO 同步 + 无账号可用 + 多模块单 App）**，但用**中文习惯的模块组合**（饮食/记账/日记）替换它的开发者工作流。真正的护城河是「数据主权 + 一个 App 装完生活」。

## 2. 正面案例：一个 App 内聚合多模块且活得好

### 2.1 滴答清单 TickTick —— 「深一个 + 环绕」的教科书

- **定位**：任务管理为绝对内核，习惯打卡/日历/番茄钟/倒数日作为「环绕模块」。
- **聚合策略**：**不是把 5 件事平铺，而是以 Task 为数据模型底座，把 Habit 做成 Task 的一种特殊形态**（可重复、带打卡统计）。日历是 Task 的时间视图，番茄钟是 Task 的计时视图。**所有模块共享同一条数据主干**，所以不冲突。
- **快速记录方式**（关键）：自然语言输入是行业标杆——输入 `Call dentist tomorrow at 3pm #personal !high` 即自动解析时间、标签、优先级、清单。全局快捷键可跨应用一键捕获。（来源：saaslens.app、redoyou 评测，2026）
- **定价**：免费版功能最慷慨的同类（无限任务/清单/子任务/番茄钟）；日历视图、时间线视图、>9 个清单、完整习惯数锁在 Premium $35.99/年。（来源：saaslens.app，2026）
- **口碑两面**：
  - ✅ 好评集中：一个 App 替代 5 个、NL 输入最好、跨 6 平台同步、ADHD 友好（4.86/5，41,000+ 条 App Store 评价）。
  - ❌ 差评集中：**「日历是基础功能不该付费」** 是最常见抱怨；**「功能密度过大，新手被淹没」** 反复出现；习惯免费额度只有 ~5 个。（来源：habi.app、saaslens.app，2026）
- **可借鉴**：✅ 用**统一数据主干 + 不同视图**来实现聚合（这与宇的「统一事项模型」思路一致）；✅ 免费版要慷慨到能完成核心闭环。
- **要警惕**：❌ 当「日历」这类**基础操作**被收费，用户情绪反弹最强——宇自用+朋友用，**不要有任何付费墙**。

### 2.2 flomo —— 低摩擦记录的黄金法则来源

- **定位**：碎片化卡片笔记，明确「先记录，后整理」，只服务「持续不断记录」这一件事。
- **模块策略**：**只做一个**，且官方主动列出「不擅长什么」（排版→石墨、导图→Xmind、协作→Notion）。这是「克制」的极致样本。
- **快速记录方式**（本次调研最重要的可复用设计）：
  1. **无标题、无分类、无反排版**——像聊天窗口一样的输入框，打开即写。**明确拒绝 Markdown、公式、自定义标题、颜色、字体**，因为「会让用户想写长篇」。（来源：help.flomoapp.com，2026）
  2. **多入口捕获**：手机长按图标、桌面小部件、PC 菜单栏图标、**微信服务号直接发消息**（中国场景的独特入口）、浏览器插件、第三方集成。
  3. **语音输入但「不做自动录音」**——创始人原话：「语音功能使用率没我们想象中高……单人短语音记想法对部分人是刚需，但不是大众需求。」**这个反共识极其重要**。
  4. **热力图**可视化反馈（flomo 最早做），提升记录动机。
- **创始人的核心洞察（原文引用）**：
  - 「flomo 的『简单』要卡在**用户有印象**的阶段：如果完全没印象，一键转发/自动保存就没意义；如果要像 Word 一样调字号，用户也不想记。」
  - 「比『记起来难』更关键的是，**用户不知道该记什么**。」
- **定价**：免费版含记录/标签/云同步/搜索；PRO 解锁每日回顾、双向链接、AI 洞察。（来源：ali213、help.flomoapp.com，2026）
- **可借鉴**：✅ 低摩擦记录三原则（见 §5 法则）；✅ 微信服务号作为输入入口——**极其适合宇的「快速记录」场景**；✅ 热力图作为习惯的正反馈。
- **要警惕**：❌ flomo 不做打卡、不做 Todo、不做日历。**这恰恰证明：记录型产品的克制是它活下来的原因。宇若把日记和复盘混在一起，等于破坏了这个规则。**

### 2.3 小卡健康 CalorieMate —— 热量模块的最低摩擦解法

- **定位**：减脂人群的 AI 营养记录，把「记录」本身做成几乎零摩擦。
- **快速记录方式**（本次调研中热量模块最佳实践）：
  1. **一句话语义记录**：说/打「我喝了一杯牛奶，跑了 5 公里」，AI 自动拆分并同时记录饮食+运动+体重+围度+喝水等 **10+ 种健康指标**。这是**北极星交互**。
  2. **AI 拍照 + AR 分量**：三层识别链（VLM 理解 → 100 万+ 中文食物库匹配 → AR 测距估体积/重量），对标「15 秒出 30 余种营养素」。
  3. **外卖小票截图识别**（美团/饿了么订单截图直接解析）——**极具中国场景洞察力**。
  4. **5 种相机模式**（日常/包装/条码/饮品/外卖），按吃饭场景拆分子引擎。
  5. **手表端独立记录**（Apple Watch / 鸿蒙），「抬手即记」。
- **定价**：核心记录（手动加食物、条码、体重、喝水、运动、同步）**永久免费不限次**；会员只覆盖依赖大模型算力的功能（AI 拍照、AI 搭子对话、AI 自定义食谱）。（来源：calmate.cc、downkuai，2026）
- **官方口径**：「彻底颠覆了传统繁琐、高流失率的手动记账模式」——**厂商自己都承认「手动记录高流失率」是这类功能的第一杀手**。
- **可借鉴**：✅ 语义记录是主线（见 §5）；✅ 按场景拆分子引擎；✅ 免费端覆盖核心闭环、AI 作为增值。
- **要警惕**：❌ 拍照识别「偶尔识别不太准，但自己调一下就行」（用户原话）——**拍照是兜底，不是主线**。

### 2.4 薄荷健康 / MyFitnessPal —— 热量模块的功能基准与「摩擦真实数据」

- **薄荷健康**：中国最早深耕饮食记录，17 年积累 **50 万条以中国食物为主**的数据（覆盖麻辣烫、螺蛳粉、食堂打菜、外卖套餐），用户 1.6 亿+。商业模式「工具→社区→电商」，营收依赖自有代餐。（来源：boohee.com、行业研报，2026）
- **MyFitnessPal**：全球最大用户规模（2.8 亿+），最大食物库（20.5M 条），条码扫描体验最佳，深度整合 40+ 穿戴设备。Premium $79.99/年。
- **⚠️ 关键摩擦/准确度数据（必须标注的硬事实）**：
  - MyFitnessPal 在 DAI 六 App 验证研究（2026-03）中，**称重餐平均 ±18% MAPE**；用户提交条目差异大（同款巨无霸热量 478-612 卡不等）；**AI 拍照「份量 consistently 偏 30-50%」**。
  - 用户抱怨高频词：**「记录一餐要点太多下」「劣化（enshittification），功能被搬进付费墙」「AI 热量计数不可靠」**。免费版广告激增。
  - 来源：calorietrackerlab.com、thesunrisedigest.com、rightaichoice.com，2026-08/09。
- **可借鉴**：✅ 食物库本地化是护城河（中餐没法用西式库解决）；✅ 条码扫描是包装食品的最快路径。
- **要警惕**：❌ 自建食物库是重资产，**宇自用阶段不应自建完整库**，而应「常吃项复用 + 语义解析 + 手动录入」轻量起步。

### 2.5 Day One / Apple Journal —— 日记模块的两种范式

- **Day One**（结构化派）：多日记本、标签、Markdown、富媒体、天气/位置/步数自动附注、On This Day 回顾、跨 iOS/Android/Web/Watch。**每日一问提示库 + 模板**帮用户「面对空白页」。$34.99/年。
- **Apple Journal**（极简派）：**Journaling Suggestions API**——用设备端 ML，从照片、锻炼、音乐、去过的地方**自动生成写作建议**（「降低开始记录的摩擦」）。刻意**不做标签、不做文件夹、不做搜索**，单一时间线。免费，仅 iPhone，且**数据难以导出**（silo）。
- **共同洞察**：两者都在解决「面对空白页不知写什么」——这正是 flomo 说的「比记起来难更关键的是不知道记什么」。
- **低摩擦日记法则**：**自动附加上下文（时间/地点/天气/照片）+ 给一个提问锚点**，用户只需补一句话，而不是从零构思。
- **可借鉴**：✅ 日记 = 自动上下文 + 轻提示；✅ 「同日回顾（On This Day）」是日记产品的情感价值顶点。
- **要警惕**：❌ Apple Journal 因「难导出 = 数据孤岛」被诟病——**对本地优先的宇而言，导出能力本身就是卖点**。

## 3. 反面案例：模块堆叠 / 变现绑架导致的崩塌

### 3.1 时光序 —— 头号警示案例（本项目的「反面对照组」）

- **它堆了什么**：**18 个模块**——待办、备忘录、倒数纪念日、目标、习惯打卡、记账、日记、番茄专注、生理期、喝水、课程表、读书笔记、闹钟、饮食体重、健康作息、还款提醒、排班表、每日先知。官方宣传「一个 App 全搞定」。
- **崩在哪**（差评/投诉集中点，来源：黑猫投诉、CNMO 测评、百度百科，2024-2025）：
  1. **多而不精，每个模块都是「点到即止的象征性功能」**。测评原话：「功能多而不精……没有突出点，新手一个月还是没摸透。」
  2. **虚假宣传 + 诱导充会员 + 客服失联**（黑猫集体投诉：「使用体验差、无客服、退款无门」）。
  3. **数据安全**：被指出**未采取加密/去标识化技术措施**，可能收集用户数据用于追踪。
  4. **数据丢失**：多条投诉「存的内容全部消失，且没有备份」。
  5. **功能不稳定**：提醒不到期、日历同步出错、注销按钮缺失。
- **核心教训**：**18 个模块平铺 ≠ 18 倍价值，而是 18 倍的维护债、18 倍的失败点、18 倍的信任消耗。** 「把功能铺满」本身就是产品质量的敌人。

### 3.2 Notion（第二大脑用法）—— 「设计即负担」的慢性崩塌

- **它堆了什么**：数据库、视图、关系、Rollup、模板、属性……理论上无限扩展。
- **崩在哪**（来源：Android Authority、r/Notion、tryultrathink，2025-2026）：
  1. **捕获摩擦太高**：每次记录需「打开 App → 找对数据库 → 新建条目 → 填属性 → 排版」，30 秒-2 分钟。有 20 次记录冲动，就等于 10-40 分钟摩擦，**结果大部分记录被跳过**。
  2. **「设计」变成目标**：用户花在「怎么组织」上的时间比「实际使用」还多。有用户下载了 **37 套第二大脑模板，一套都没长期用**。
  3. **维护成本复利增长**：数据库越大越慢，属性越久越不一致，「系统反过来惩罚你记录得越多」。
  4. **ADHD 用户直接弃用**：原话「从一个 App 切到另一个，我就忘了要记什么」。
- **核心教训**：**灵活性 = 决策成本。聚合型产品必须替用户做组织决策（默认值预填），而不是把决策权丢回给用户。**

### 3.3 随手记 / 鲨鱼记账 —— 「变现方式杀死产品」

- **它堆了什么**：记账 + 理财社区 + 推荐 + 会员体系 + 广告位。
- **崩在哪**（来源：今日头条测评、什么值得买、小红书，2026）：
  - **随手记**：启动慢、弹窗多、广告频繁；**导出数据被拆层收费**（普通账本导出另收 30 元；2026 年鸿蒙用户账本被强制升级为「神象账本」后导出变年费制）。老用户集体「告别帖」——**「不是记不了账，是账带不走了」**。
  - **鲨鱼记账**：「3 秒记账确实快，但免费版每点三次弹一次广告，开屏 3 秒起步，首页推理财课」。用户原话：「打开鲨鱼是为了记一笔外卖，结果先被推荐基金。」**「记账用五秒，关推荐用十秒。」**
  - 共同套路：**基础免费 → 等你记了几千笔 → 发现导出/多账本/预算全要会员**。
- **核心教训**：**对一个自用+朋友用的产品，数据导出必须从第一天就免费无锁**——「账带不走」是用户抛弃产品的第一触发点。同时，**任何广告位都属于「产品地位的自我否定」**。

### 3.4 Logseq —— 本地优先阵营的「理想主义崩塌」

- **它堆了什么**：不是堆模块，而是**用 4 年做一次架构重写**（Markdown 文件版 → SQLite 数据库版）。
- **崩在哪**（来源：deshittify.io、bundl.run、Hacker News、r/logseq，2026）：
  - 2024-04 到 2025-05 **13 个月无稳定版发布**，社区出现「Is Logseq dead?」，用户大规模迁移到 Obsidian / AFFiNE。
  - 同步多次导致数据丢失/文件损坏，用户形容「灾难性」。
  - 2.0 版**存储层不再是 Markdown 文件**（变成 SQLite），「笔记不能再被外部文本编辑器手改」——**背离了本地优先的核心承诺**。
  - 官方自带「data loss is possible」警告。
- **核心教训**：**本地优先产品的信任建立在「数据永远是你能直接读的普通文件」之上。一旦为了性能/协作牺牲这一点，就失去了存在的理由。** 对宇而言：**第一版架构要稳，不要让「重写」吃掉产品。**

### 3.5 Super App / 功能膨胀的通用规律（理论支撑）

- 来源：Forrester《The Super App Window Has Closed》(2023)、zamin.uz、jiaweing.com、Sidekick Interactive 案例（2026）：
  - **Uber 主动把 Uber Eats 拆成独立 App**——「保持每个 App 的专注，才能给每个服务优化过的体验」。
  - 福雷斯特：Super App 只在「移动互联网爆发期 + 竞品未建立 + 金融基础设施缺口」这类特殊条件下成立，**这些条件今天已不存在**。
  - 一个健身 App 案例：把「饮食+训练+社交+电商」堆在一起，体积 200MB、留存 <5%；砍到只做训练后**留存升到 40%**。
  - **判断标准雏形**：「服务必须『走在一起』——互相补充、在同一条路上。」（Yandex Go 只做移动场景，不塞音乐电影。）

## 4. 特别调查：本地优先 + 可自建部署的同类竞品

这直接决定**宇该对标谁**。

| 产品 | 定位 | 存储 | 同步 | 自建 | 用户为什么选它 |
|---|---|---|---|---|---|
| **Obsidian** | 本地 Markdown 知识库 | 纯 Markdown 文件 | 官方 Sync（付费）或任意文件同步 | ✅（文件层） | 数据是完全开放的普通文件；4300+ 插件；10,000 篇笔记仍毫秒级 |
| **Joplin** | 开源隐私笔记 | Markdown | 自带 E2EE，可走 Nextcloud/WebDAV/S3 | ✅（含 Joplin Server） | 开源 + 同步前加密，存储方也读不了；冲突时保留副本不覆盖 |
| **Logseq** | 大纲式双向链接 | Markdown→SQLite（2.0） | 官方 Sync（beta，~$5/月） | 部分 | 大纲 + Daily Journal 工作流；但见 §3.4 崩塌 |
| **Actual Budget** | 开源信封记账（YNAB 替代） | 本地 SQLite | 单 Docker 容器自建同步，E2EE | ✅ 极简（单容器） | 完全免费；自建后数据不出门；比 YNAB 快；Mint 关闭后的避风港 |
| **Super Productivity** | 开源任务+时间追踪 | 本地 | BYO：WebDAV/Nextcloud/Dropbox 或自建 | ✅ | **本地优先 + 无账号可用 + 自带多模块 + 可自建同步** |

### 4.1 用户为什么选本地优先而不选云端 SaaS？（提炼）

1. **数据主权 / 抗关停**：Mint 关闭、Logseq 同步灾难、随手记导出收费——**「公司会涨价、会改版、会关停，只要文件在我手上，我的东西就锁不走」**。（来源：flexnote、vucense，2026）
2. **离线完整可用**：真正本地优先 = 数据默认在本地、完全离线可用、文件可带走。
3. **无订阅税 / 无劣化**：不会被「功能搬进付费墙」二次收割。
4. **正确理解「本地优先 ≠ 离线独占」**：本地优先仍可同步和分享，**只是「由你决定数据住在哪」，而不是被锁在官方云**。

### 4.2 ⚠️ 本地优先的真实代价（宇必须提前知道）

- **同步是你的事**：Actual Budget「运行在 512MB VPS 上」这句话默认你懂 VPS、愿意维护、会打补丁。Super Productivity 用户反馈 **「Nextcloud 自建同步偶发数据损坏、任务回滚」**——这是它最大问题。
- **移动端是薄弱点**：Actual Budget 移动端「passable but not polished」，且「不是给你站在柜台前记咖啡用的」——**它是给每周坐下来复盘用的**。
- **迁移/学习曲线**：Obsidian 初始配置耗时、插件需自己维护；Logseq 大纲模型不适合所有人。
- **结论**：**本地优先的「架构」可以抄，但「把同步维护成本转嫁给用户」这个坑，宇靠「部署在自己 NAS + 内网穿透」已经天然缓解了**——这是宇方案相对开源阵营的**结构性优势**，应作为核心卖点。

### 4.3 对标结论（直接回答「该对标谁」）

| 维度 | 该对标 | 不该对标 |
|---|---|---|
| 架构 | **Super Productivity**（本地优先 + BYO 同步 + 无账号可用 + 多模块单 App） | ❌ Obsidian（纯文件，无结构化数据模型，不适合「事项+数值」混合） |
| 数据信任 | **Obsidian / Joplin 的文件可带走 + Joplin 的 E2EE** | ❌ Apple Journal（数据孤岛，难导出） |
| 记账模块的功能深度 | **Actual Budget**（本地优先记账的 UX 天花板） | ❌ 随手记（广告+导出收费的变现模式） |
| 多模块聚合的「度」 | **TickTick**（统一数据主干 + 环绕模块） | ❌ 时光序（18 模块平铺） |
| 低摩擦记录 | **flomo（记录）+ 小卡健康（热量）** | ❌ Notion 第二大脑（设计即负担） |

**一句话**：**宇的产品 = Super Productivity 的架构信心 + TickTick 的聚合克制 + flomo/小卡健康的录入范式 + Actual Budget 的数据主权，用中文生活场景（饮食/记账/日记）替换开发者工作流。**

## 5. 交互范式：低摩擦录入的可复用设计（本次调研最重要的产出）

### 5.1 通用黄金法则（跨模块）

来自 flomo 创始人的原始洞察 + 各产品实践，提炼为 **5 条铁律**：

1. **入口无处不在，而非藏在 App 里**。flomo：微信服务号/长按图标/桌面小部件/PC 菜单栏。Super Productivity：全局快捷键跨应用捕获。**宇的对应**：NAS + 内网穿透天然可做 Web 快捷入口，再配手机桌面小组件。
2. **默认值预填，绝不要求用户做分类决策**。Notion 崩在「要你先当架构师」。**宇的统一模型要「自动带默认形态/领域/跨度」，用户可改可不改。**
3. **一屏内完成，且能一步跳过**。低摩擦 = 「允许不完整记录」。flomo 的「用户有印象」原则：**不能简化到用户没动脑（那样记下来没用），也不能复杂到用户不想记**。
4. **自动附加上下文**（时间/位置/天气/照片），用户只补一句话。Day One / Apple Journal 的核心。
5. **正向反馈可视化**。flomo 的热力图、TickTick 的 streak——「让格子被填满」提升记录动机。

### 5.2 记账模块：摩擦阶梯（从高到低）

| 方案 | 摩擦 | 真实评价 | 是否推荐 |
|---|---|---|---|
| 手动选分类+金额+备注（三步） | 高 | 鲨鱼记账「3 秒」是能手速下的上界，**不是目标** | ⚠️ 兜底 |
| **通知栏/短信自动抓取 → 一键确认** | **极低** | 一木记账「付完款，浮出卡片，点确认即可，全程不用进 App」 | ✅✅ **首选** |
| 语音记账（「午饭 30块」） | 低 | 各家中普遍，但只是「语音识别」，非真 AI 自动记账 | ✅ 有效但非颠覆 |
| 截图识别小票/外卖订单 | 低 | 小卡/飞鸭支持，中国场景高价值 | ✅ 值得做 |
| 快捷模板 / 小组件一键记 | 低 | 小薯条「无需打开 App 直接录入」 | ✅ 值得做 |
| 自动分类 | — | 需历史数据训练，冷启动期不可靠 | ⚠️ 二期 |

- **噱头识别**：多数 App 宣传的「AI 自动记账」**其实只是语音识别**（「你说个数它记一下，跟 Siri 设闹钟没区别」）。真正意义上的「消费完成自动触发」目前只有少数（如一木、飞鸭）做到，且**飞鸭把真 AI 放在付费墙后**。
- **对宇的建议**：**「通知/短信抓取 + 一键确认」是记账模块的北极星**；手动记账保底 ≤2 步。宇自用+NAS 部署，可考虑直接读手机通知（需权限）或做粘贴解析，成本可控。

### 5.3 热量模块：摩擦是「第一流失点」——这是硬证据

- **厂商自认**：小卡健康官方称其 AI 记录「彻底颠覆传统**高流失率**的手动记账模式」。MyFitnessPal 用户抱怨高频词：**「记录一餐要点太多下」**。
- **摩擦阶梯（从高到低）**：
  1. 手动搜索食物库 + 称重（最高，美式精细记录，中国用户没耐心）
  2. 搜索 + 常吃项复用（中）
  3. 条码扫描（包装食品最优，但中餐场景少）
  4. **一句话语义（「一碗米饭两个鸡蛋」「跑了5公里」）** ← **北极星**
  5. AI 拍照 + AR 估份量（低操作，但**份量误差 30-50%**，只能兜底）
  6. 外卖小票/订单截图识别（中国场景，极低摩擦）
  7. 手环/手表自动同步运动消耗（零输入，但见下）
- **运动消耗估算的真相（必须如实告知用户）**：
  - 主流方法：`消耗 = MET × 体重(kg) × 时长(h)`（MET 为标准活动强度系数，1 MET ≈ 静息代谢）。
  - **手环/手表误差 20-40%（meta 分析），个别达 27-93%（斯坦福 2017 研究）；力量训练最差（30-50%+）。**
  - 原因：腕部传感器测量不到无氧做功；且**手环倾向高估（含静息代谢的 gross 值），厂商算法为「参与感」而非精度调优**。
  - **实用建议（给宇的产品文案）**：运动消耗**当作相对趋势指标，不要当成「赚来的热量额度」去吃掉**——「运动补偿陷阱」会抹掉 50-75% 的实际消耗。
- **对宇的建议**：
  1. 摄入侧：**一句话语义为主 + 常吃项复用 + 拍照兜底**，不自建完整食物库（用 100-200 条常吃项 + 语义近似起步）。
  2. 消耗侧：**优先读手环/手表数据（连接 Apple Health / 华为运动健康）**，用 MET 公式作为无设备时兜底，**UI 上明确标注「估算值」**。
  3. **拒绝「必须精确」的执念**——用「±25% 趋势」而非「精确卡路里」来设计反馈。

### 5.4 日记 / 随笔模块：低摩擦 + 「必须与复盘分开」

- **flomo 式**：无标题、无分类、只管写；多入口捕获；热力图反馈。**核心是「不要求组织」。**
- **Day One 式**：每日一问提示库 + 模板 + 自动附加天气/位置。
- **Apple Journal 式**：系统级建议入口（从照片/锻炼/位置自动生成写作锚点）。
- **黄金法则**：「日记是**容器**，复盘是**分析**」。**两者数据模型不同、情绪不同、入口不同**：
  - **日记（随心记）**：低预期、无产出压力、允许碎片、强调「记录当下」——目标是**持续**。
  - **复盘**：结构化、周期性（周/月）、需要回看聚合数据、强调「提炼」——目标是**洞察**。
  - **混在一起的后果**：用户会因「要复盘」的压力而不敢随便写日记 → 日记流失；或日记流太杂导致复盘无从下手。这正是 **flomo 不做打卡**的原因（「打卡会扭曲用户行为」）。
- **对宇的建议**：日记模块 = **flomo 式无压力输入 + 自动时间/领域上下文 + On This Day 式回顾**；复盘是**读日记+数据后单独产出的结构化文档**，两者**不共享编辑入口**。

### 5.5 通用能力（跨模块共享）

| 能力 | 具体做法 | 来源 |
|---|---|---|
| 全局快捷入口 | 桌面小组件 / PC 菜单栏 / 微信服务号 / 全局快捷键 | flomo、Super Productivity、TickTick |
| 自然语言解析 | 中文日期/时间/数量/分类自动识别（「明天下午3点」「午饭30块」「一碗米饭」） | TickTick（标杆）、小卡健康 |
| 默认值预填 | 形态/领域/跨度自动带默认，可改可不改 | 反 Notion 教训 |
| 一屏完成 | 允许不完整记录，先存后整 | flomo「先记录后整理」 |
| 离线优先 | 所有录入路径必须离线可用 | 本地优先架构 |
| 数据可带走 | 导出必须免费无锁、格式开放（Markdown/CSV/JSON） | 反随手记教训 |

## 7. 核心问题：功能聚合 vs 专用工具的边界在哪？

### 7.1 判断标准（可操作，非含糊）

一个模块**该聚合进主 App**，当且仅当**同时满足**以下 **4 条**（满足 2 条以下坚决外包）：

| # | 判据 | 说明 | 反例（该外包） |
|---|---|---|---|
| **1** | **数据能被「今日/领域」视图复用** | 该模块的产出能进入「今日视图」或「领域页」，与其他模块形成一张上下文网 | 看剧进度、游戏存档——无法复用 |
| **2** | **与已有模块共享同一次决策** | 用户做这件事时的动机与其他模块同源 | 「热量摄入」和「今日训练」同属健身闭环 → 聚合；「股票行情」与健身无关 → 外包 |
| **3** | **录入能压缩到「一句话/一键」级别** | 若该模块天然需要高摩擦录入（如专业记账的复式记账），聚合只会拖累主 App | 专业报税、投资组合追踪 → 外包给专业工具 |
| **4** | **深度可接受「够用」而不追求「权威」** | 聚合模块是「80 分」，专业 App 是「99 分」。若用户需要 99 分（如财务合规、医学营养），必须外包 | 医疗级营养处方、企业财报 → 外包 |

### 7.2 用这套标准检验宇的三个新模块

| 模块 | 判据1 复用 | 判据2 同决策 | 判据3 低摩擦 | 判据4 够用即可 | 结论 |
|---|---|---|---|---|---|
| **记账** | ✅ 可进「今日/个人」视图 | ⚠️ 独立闭环，但与「个人」领域相关 | ✅ 通知抓取+一键确认可做到 | ✅ 日常流水够用（非报税） | **聚合（但独立数据模型+独立入口）** |
| **热量摄入/消耗** | ✅ 进「健身」页，与训练同屏 | ✅✅ 与健身习惯同一闭环 | ✅ 一句话语义可做到 | ✅ 减脂够用（非医学处方） | **聚合（健身领域内，与训练强绑定）** |
| **日记（随心记）** | ✅ 进「今日」，与情绪/事件关联 | ⚠️ 独立但属「个人」 | ✅ flomo 式无压力 | ✅ 自用足够 | **聚合（独立入口，绝不与复盘混）** |

**三个模块都通过检验 → 可以聚合。但请注意：通过检验 ≠ 塞进统一事项模型。** 见下。

### 7.3 一个个人工具装几个模块才不崩？—— 分档标准

综合时光序（18 个崩了）与 TickTick（5 个活了）的对比，提炼**「模块承载力」三层模型**：

| 档位 | 模块数 | 特征 | 例子 |
|---|---|---|---|
| **安全区** | **3-6 个** | 每个模块共享统一数据主干，或落在同一「领域」闭环内 | TickTick(3-4)、本项目目标(收集+今日+记账+热量+日记=5) |
| **警示区** | **7-12 个** | 开始出现「象征性功能」，维护债上升 | 多数记账「全家桶」 |
| **崩塌区** | **13+ 个** | 每个模块都点到即止，必然出现稳定性/信任问题 | 时光序(18) |

**宇的目标 5-6 个模块正在安全区上沿。** 关键约束：

1. **形态标签不是模块**。习惯/待办/计划是「同一事项的三种形态」，**共用一个数据模型 + 三个视图**，不算 3 个模块。这是宇设计里最聪明的地方。
2. **领域是组织轴 = 天然的「防膨胀」机制**。新需求必须先回答「它属于健身/学习/工作/个人哪个领域」，否则不进。**领域数量应冻结在 3-5 个**。
3. **每个模块必须有「独立数据模型」**。记账有金额/分类/账户，热量有食物/卡路里/MET，日记有正文/情绪——**它们本质不同，不能强行塞进「统一事项」。** 统一的是**入口体验和导航（今日视图 / 领域页）**，不是**数据表**。

### 7.4 什么该坚决外包？（明确清单）

| 需求 | 为什么外包 | 外包给谁 |
|---|---|---|
| 专业级财务/报税/投资组合 | 需 99 分准确度 + 合规 | 专业财务软件 / 券商 App |
| 医学级营养处方 / 疾病饮食 | 需专业权威 | 医院 / 注册营养师 |
| 深度知识管理（双向链接/研究） | 与「生活执行」语境不同，会拖垮主 App | Obsidian / Logseq |
| 团队协作 / 项目甘特图 | 需多人权限模型 | Notion / 飞书 / ClickUp |
| 长文写作 / 出版 | 排版需求与「快速记录」冲突（flomo 已证明） | 石墨 / Word / Ulysses |
| 社交 / 社区 / 比较排行榜 | 会扭曲个人记录行为（flomo 明确拒绝打卡） | 不外包，**直接不做** |

**一句话原则**：**「生活执行的 80 分」聚合，任何「专业领域的 99 分」外包。**

## 8. SWOT（针对本项目）

| | 内部 | |
|---|---|---|
| **优势 S** | 1. **本地优先 + NAS 自建**——天然规避「同步维护成本转嫁」这个开源阵营最大坑；2. **统一事项模型**——用「形态视图」替代「模块堆叠」，是防膨胀的结构性设计；3. **领域主轴**——天然的模块准入过滤器；4. 无商业化压力 → **可以做到完全无广告、无付费墙、数据免费导出**。 |
| **劣势 W** | 1. 单/少数开发者，**维护带宽有限**（参考 Logseq 重写吃垮项目）；2. 自建食物库/记账规则是重资产，冷启动难；3. 移动端体验（尤其录入）若不如原生 App，用户不会用；4. 内网穿透的可用性/稳定性依赖宇的技术运维。 |
| **机会 O** | 1. **市场空位**：无竞品同时做到「本地优先+自建+多模块生活聚合」；2. 「复盘」被普遍忽视，有差异化空间；3. 用户对 SaaS 劣化（涨价/关停/导出收费）的疲劳是时代级顺风；4. 中文生活场景（食堂打菜、外卖小票、微信入口）是海外产品无法复制的护城河。 |
| **威胁 T** | 1. **范围蔓延**（宇已说「可能还有没考虑到的场景」——这正是时光序的起点）；2. 模块越多，稳定性和数据安全风险越大（时光序数据丢失即前车之鉴）；3. 朋友使用带来「多用户」复杂度（权限/备份/客服），可能拖垮单人维护；4. 本地优先的数据丢失风险需自担。 |

## 9. 战略建议

### 9.1 差异化投资（该重点做的）
1. **把「本地优先 + NAS 自建 + 数据免费导出」做成核心卖点**，而不是技术实现细节。这是对标 Super Productivity / Actual Budget 的信任根基，且是时光序这类云产品的死穴。
2. **「今日视图」作为统一聚合层**——所有模块（含记账/热量/日记）的当日产出都汇总到这里。这是「聚合感」的来源，也是与专用工具的分水岭。
3. **低摩擦录入三件套**：热量=一句话语义、记账=通知抓取+一键确认、日记=无标题即时写。**这是决定留存的胜负手**（厂商自认手动记录高流失）。
4. **复盘独立成模块**，且明确与日记分离——做「读数据 + 读日记 → 产出结构化洞察」，填补市场空位。

### 9.2 追平领域（该做但不追求顶尖）
- 习惯打卡的 streak/统计（对标 TickTick，够用即可）。
- 食物库（不自建全库，用常吃项 + 语义近似 + 拍照兜底）。
- 记账分类/报表（对标 Actual Budget 的可用度，不做复式记账）。

### 9.3 防守策略（该避免的）
1. **冻结模块数在 5-6 个、领域数在 3-5 个**。任何新需求先过 §7.1 的 4 条判据。
2. **架构第一版就要稳**（反 Logseq 教训）——**不要让「重写」吃掉产品**。数据结构宁可简单可迁移。
3. **上线前必须有自动备份 + 一键导出**（反时光序数据丢失教训）。
4. **零广告、零付费墙**（反随手记/鲨鱼教训）。
5. **朋友使用场景要谨慎**：第一版建议**保持「单人为主 + 朋友只读/极简共享」**，避免过早引入多用户权限体系。
