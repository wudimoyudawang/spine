## 📌 TL;DR（3-5 行）

1. **v1.0 是一个整体目标，但施工分 7 个阶段（Stage 0–6），每个阶段末尾都有一个"能真的打开它用起来"的可运行验收点（A0–A6）。** 核心原则：**「四个模块都要」≠「四个模块一起做完才第一次能跑」**。
2. **Docker 与开源仓库基础前移到 Stage 0，不留最后。** 容器化是**部署方式的决定**，会反向约束配置外置与后端设计——晚做=返工。
3. **同步预留 7 项（UUID / 墓碑 / rev / device_id / 加密边界 / UTC / 导出可重入）从"前瞻预留"升级为"Stage 5 的输入契约"**，仍然是最不可回溯的决定。
4. **范围扩大有真实代价，不假装没有：** 工期由原分阶段方案的约 **45–65 人日**膨胀到约 **110–160 人日 [估]**（2–3 倍）；测试覆盖、打磨度、边界处理、文档四方面都要做取舍。
5. **四模块同时上线 → 无法归因**，因此**模块级熔断的重要性大幅上升**，已给出四个模块各自的阈值、动作与冷却期（§6）。

## 1. 排序框架与口径调整说明

### 1.1 口径替换（沿用 v1，继续生效）

| 原口径 | 替换后 | 理由 |
|---|---|---|
| 业务价值（收入 / 获客 / LTV / 付费转化） | **用户留存价值** —— 该项对「宇是否还在用」的贡献度 | ① 单用户自建部署，无收入与获客，原口径恒为 0，无法区分需求（数析 §6.0「分母为 1」）；② feature fatigue（Thompson et al., 2005，A 级）证明「吸引选择」≠「留住使用」——单用户产品的生死线是留存；③ 与北极星同向，避免"指标好看但事情没变" |

### 1.2 v2 中评分的作用变了（重要）

范围已被宇锁定，**评分不再用于"做 / 不做"，而用于两件事**：
- **① 施工顺序**：同阶段内，谁先做（分数高、依赖少者先做）。
- **② 熔断优先级**：一个模块需要被降级/移除时，**先动分数低、且"记录后使用率"低的那个**。

| 因素 | 权重 | 评分方向（1–5 分，越高越好） |
|------|------|---------|
| 用户影响 | 30% | 5 = 影响场景最多、痛点最严重 |
| 用户留存价值 | 25% | 5 = 直接决定「还回不回来」 |
| 战略对齐 | 20% | 5 = 高度契合 D1–D5，尤其「减少信息分散」+「能被今日视图吸收」 |
| 工程成本 | 15% | **5 = 成本最低/最易实现（反向）** |
| 依赖风险 | 10% | **5 = 依赖最少/风险最低（反向）** |

**总分 = (0.30×影响 + 0.25×留存 + 0.20×战略 + 0.15×成本 + 0.10×依赖) × 20**（0–100）。

## 4. v1.0 必须为同步预留的技术决策 ⭐（v2 核心章节 · 保留并加强）

> **v1 的最正确判断，v2 继续保留。** 且因**同步已进入 v1.0 范围**（不再是"将来的第二阶段"），这 7 项从"前瞻预留"升级为 **Stage 5 的直接输入契约**——**若现在不做，Stage 5 一定要重写已存数据**（Logseq 教训，竞析 §3.4）。
> 好消息：**这 7 项只占 Stage 0 很小的工作量**，却是全路线图里最不可回溯的决定。

### 4.1 必须在 Stage 0 定死的 7 项

| # | 技术决策 | 为什么必须现在定 | 若不定会怎样（代价） | 推荐方案 |
|---|---|---|---|---|
| **T1** | **ID 生成方式** | 多设备离线创建再合并 | 自增整型 → 两台设备各自生成 `id=1,2,3…` → **必然冲突**，合并时被迫全量重编 ID（=重写） | **客户端生成 UUIDv7**（时间有序、索引友好）。**禁止自增整型。** 最便宜、最不可回溯的一项 |
| **T2** | **软删除 + 墓碑** | 删除必须可同步 | 硬删除 → 离线设备回连时**把已删记录复活** | 所有表加 `is_deleted` + `deleted_at`；**禁硬删**，删除=打墓碑 |
| **T3** | **每记录版本 / 时钟** | 需要可判定的冲突依据；**设备时钟会漂移** | 仅靠 `updated_at` 做 LWW，会因时钟偏差误判新旧 | 每条记录带 **`rev`（单调版本）+ `updated_at`（UTC）**；冲突用 **`rev` 优先、`updated_at` 兜底**（简单可迁移的 LWW，**不引入 CRDT**） |
| **T4** | **`device_id` / `owner_id` 占位** | 冲突归因 + 多用户 | 后补字段= schema 迁移；权限模型无处挂载 | 所有表带 `device_id` + `owner_id`（Stage 0–4 恒为本地单用户常量）。**成本极低，给 Stage 5 的"保险"** |
| **T5** | **随心记的加密边界** ⭐ | 若明文存、到 Stage 5 才改 E2EE，**要全量重加密迁移**；且"朋友可见"世界要求它**架构级不可读**（瑞思 §2.3） | 迁移时若算法变更 → 历史条目无法解密/泄露；导出/备份可能夹带明文 | **条目级密文存储**：`is_private=true` 只存**密文 + nonce**，带 `enc_version` 便于演进；**密钥不与数据同存**；**导出默认排除明文**（除非用户显式选择）。按**条目**而非整库加密，才与 E2EE 同步兼容 |
| **T6** | **时间统一 UTC（+ 可选时区）** | 跨设备、跨时区一致 | 存本地时间 → 换设备/改时区后错乱且不可逆 | 统一存 **UTC**；`Log.ts`（事件发生）与 `created_at`（记录系统）**分离** |
| **T7** | **导出 schema 含同步字段 + 可重入** | 「一键导出」是主理人裁定的主存策略；导出可还原=100% 是数据主权根基 | 导出缺 `id`/`updated_at`/`device_id` → 重导入无法对上，还原率 <100%；开源后用户迁移失败 | 导出（JSON/CSV/Markdown）**必须含 T1–T4 字段**；导入**幂等**（同一 `id` 重复导入不产生重复行） |

> **统一要求**：T1–T7 不仅落在 `Item`，还落在 **`Log`、`Template`**。**Stage 0 就要有 schema migration 版本机制**（开源后老用户升级依赖它）。

### 4.2 存储策略（主理人已裁定）

- **主存 = SQLite**（事务、索引、聚合查询天然适合「事项 + 数值」混合）。
- **不做事实时双写镜像**（裁定）。改为**内置一键导出**（JSON + CSV + Markdown），**随时可导出**，并保证**任意时刻都能从导出文件完整还原**（D2 指标 = 100%）。
- **守信任承诺**：SQLite 是二进制，需通过**① 一键导出始终可用 ② `Stage 0` 就验证"导出→空环境→还原"三步 100%** 来对冲"数据锁死"风险（反 Logseq「2.0 变 SQLite 后不可外部手改」教训）。
- **数据目录 / 配置 / 密钥三分离**（为 Docker 挂载与开源安全）：数据卷 ≠ 配置 ≠ secrets，且后两者永不进仓库。

### 4.3 可以（也应该）推迟的项

| 推迟项 | 为什么可以推迟 |
|---|---|
| 实际同步协议 / 传输方式（HTTP API vs WebDAV） | 数据契约（§4.1）不变，传输方式随时可换 |
| CRDT / 协同引擎（Yjs、Automerge） | **Stage 0–4 坚决不引入**——"过早的深度"，与「数据结构简单可迁移」冲突。T3 的 LWW 足以覆盖"单人为主 + 朋友只读" |
| 完整多用户权限模型 | Stage 5 先做"单人为主 + 朋友只读/极简共享"；**T4 的 `owner_id` 占位已足够** |
| 冲突解决 UI | Stage 5 后期；先保证"冲突可人工解决" |
| 加密封装的最终算法 / 密钥派生细节 | 可逐步定；**但 T5 的"边界与字段"必须 Stage 0 定** |

### 4.4 Stage 0 就要跑的验证法（把"不重写"变成可验收）

1. **导出 → 空环境 → 还原**：数据完整率 = **100%**（D2）。
2. **模拟双端**：拷一份当"设备 B"，A/B 各改同一条 + 各删一条 → 按 T1–T3 合并 → 验证**无 ID 冲突、无删除复活、冲突可判定**。
3. **随心记加密验证**：备份/导出文件中**不含随心记明文**。

**通过标准**：三步全过，方认为契约有效。**这是全路线图唯一一条"技术防重写"硬验收。**

## 5. 【范围扩大的代价】诚实评估

> 宇强制扩大了范围（四模块全部 + 热量完整版 + 后端同步 + 开源 + Docker）。**我们尊重决定，但不能假装没有代价。** 以下是真实的取舍。

### 5.1 工期：膨胀约 2–3 倍

| 方案 | 到"可日常使用"的工期 [估] | 到"v1.0 全部交付" [估] |
|---|---|---|
| v1 分阶段方案（v0.1 + v0.2） | 25–35 人日 | —（四模块不在同一版本） |
| **v2 单一 v1.0 方案** | 约 45–60 人日（Stage 0–1） | **约 110–160 人日** |

> **口径**：单人全栈、1 人日 = 1 个专注工作日。[估] 无公开基准，**须以 Stage 0–1 的实际用时校准后续估算**。

### 5.2 四项质量取舍（必须提前认账）

| 维度 | 会发生什么 | 建议的应对（保住下限） |
|---|---|---|
| **测试覆盖** | 后端 + 同步 + 多用户让测试面**爆炸**（双端/冲突/权限/时区）；单人无法全覆盖 | **只在"关键路径"做自动化**：① 导出还原 ② 同步冲突 ③ 数据隔离（**一票否决项**）④ 加密不泄露。其余靠手工冒烟。**明确写下"哪些不测"** |
| **打磨度** | 热量完整版 UI、复盘可视化会被工期挤压 | **分级打磨**：核心闭环（Stage 1）与复盘（价值兑现点）做 90 分；热量半精/精记做 **80 分（够用即可，竞析 §7.1 判据 4）**；**接受"够用"而非"权威"** |
| **边界处理** | 跨时区、并发编辑、删除复活、**密钥丢失恢复**最易被跳过 —— 而它们恰是**数据丢失/泄露**的来源 | 把 §4.4 的三步验收 + **密钥丢失恢复流程**列为 Stage 0/5 的**必做**，不得裁掉 |
| **文档** | 开源后文档从"可选"变"必需"（部署/配置/迁移/贡献），会挤占功能时间 | 文档**随 Stage 走**（Stage 0 起 README 骨架，Stage 6 收口），不留到最后补 |

### 5.3 一个必须点出的结构性风险：两个高风险项叠加 + 无法归因

- **热量完整版**（摩擦最高、放弃最狠的品类）× **后端同步**（最复杂、最易数据事故）在 v1.0 内**同时存在**。任一项出问题，都会拖垮整体感知。
- **四模块同时上线 → 无法归因**：出问题时说不清是"哪个模块导致的"。v1 的"28 天实验、同时只上一个模块"的归因优势**已不存在**。
- **缓解**：**模块级埋点必须从 Stage 1 就分开打标**（按模块统计记录密度/回看率/耗时）；**模块级熔断独立生效**（§6）；**R1 摩擦税红线**（核心指标恶化 >20% 立即回滚）依然有效。
- **维护带宽**：后端 + 同步 + 多用户显著抬高**长期维护债**（安全补丁、依赖升级、朋友支持）。开源后还会有**外部 issue/PR**。竞析已警告单人维护带宽（Logseq）。**建议：明确"朋友只读优先、外部贡献走 issue 为主"**。

## 6. 模块级熔断规则（强化版）⭐

> 因四模块**同时上线、无法归因**，熔断机制的重要性大幅上升。除通用框架外，**给出每个模块各自的阈值、动作与冷却期**。
> **通用窗口**：28 天覆盖第 2–5 周放弃悬崖；14 天为"降级"短窗；30/60/90 天为"僵尸/移除"长窗。

### 6.1 通用框架（沿用并强化）

**四条一票否决红线：**
- **R1 摩擦税**：引入某模块后核心指标（TtC 或逃逸率）恶化 >20% → **立即回滚**该模块，无论它自己表现多好。
- **R2 赤字框架禁令**：任何模块不得引入红/绿赤字（只允许百分比 / 趋势方向 / 中性陈述）。
- **R3 完整性禁令**：任何模块不得强制完整（必须允许"只记一半"也能保存并产生价值）。
- **R4 归因隔离**：模块级埋点必须分开打标；**任一模块触发降级/移除时，一次只动一个模块**（否则仍无法归因）。

### 6.2 四模块各自的熔断阈值

| 模块 | 🔻 降级触发 | 降级动作 | ❌ 移除触发 | 移除动作 | 冷却期 |
|---|---|---|---|---|---|
| **记账** | 连续 **14 天**"有记账天数"<2/7 **或** 月度账单回看 <1 次（**只记不看 = 无价值**，优先看回看率而非记录率） | 移入「个人」领域页折叠，撤掉首页卡片；数据保留 | 连续 **60 天**零记账 | 移除导航入口（数据保留 + 可一键恢复） | 降级后 **30 天**内不得升回主导航；回主导航需连续 14 天 ≥3/7 |
| **热量** | 连续 **14 天**记录密度 <2/7 **且** 单条录入中位耗时 >30s 的占比 >50% | **自动退化为"粗记模式"**：隐藏半精/精记，保留粗记 | 连续 **60 天**零记录 | 移除入口（粗记数据保留 + 可导出） | 退化到粗记后 **30 天**内不得再解锁半精/精记 |
| **随心记** | **不以使用量熔断**（低使用是它的正常态，瑞思 §4.4：不写≠失败）。信号改为：用户**关闭了"进入复盘聚合"开关**，或内容长度/频次**骤降且无理由** | **不改模块，改策略**：把默认隔离**改回硬隔离**，并核对加密边界是否生效 | 连续 **90 天**零写入**且用户主动确认** | 移除入口（本地加密数据保留） | **无冷却期**（禁止任何催促/红点） |
| **复盘** | 连续 **3 个周期**未打开 **或** 结论回写 Item <1 条/周期（**只看不改 = 退化成报表**，风险 R4） | 从导航一级移入「今日」角落入口；保留只读视图 | 连续 **90 天**零打开 | 移除入口（保留只读 + 数据） | 降级后 **30 天**内不得升回一级导航 |

> **四个模块里，随心记是唯一"低使用不触发熔断"的例外**——因为它的价值在于"写完即沉底"，而非使用频率。这条必须有，否则会把最该保护的功能误杀。

### 6.3 加新模块的准入闸门（仍保留，用于"停车场"场景）

> 范围锁定后，此闸门**仅用于未来的需求蓄水池（B5–B13）**，不用于本期四模块。
- **G1 习惯已形成**：核心捕获密度 ≥5/7、逃逸率 <20% 不升、逾期未收口 ≤10 不增、TtC 达标，**连续 21 天**。
- **G2 摩擦预算**：单条录入 ≤30s、不增核心路径步数、导航仍 ≤5、通过「一句话测试」。
- **G3 熔断先写**：引入前写下保留/降级/砍掉判据与试用期。
- **瑞思 C1/C2/C3**：锚点唯一（只今日视图负责"每日打开"）· 摩擦守恒（不增统一入口步数）· 活跃度门限（连续 4 周零使用→降权不移除）。

## 8. 利益相关者沟通要点

> 受众是**宇本人**——他既是产品负责人，也是开发者，现在还兼开源项目的维护者。分两个视角。

### 8.1 给「开发者 / 维护者」视角（宇写代码、发开源时看这段）

**范围已经扩大，你的第一敌人从"功能不够"变成了"跑不起来"。** 所以 v2 的核心纪律是：**每个 Stage 结束都必须有一个你真的能打开来用的版本**（A0：`clone → docker up → 记一条 → 导出`；A1：单机日常可用；……）。**绝不允许"全部做完才第一次运行"**——那是自建项目的头号死法。具体三件事请务必前移，晚做必返工：**① Docker 最小容器 + 配置外置（Stage 0）**——部署方式会反向决定你的后端怎么设计；**② 数据契约 7 项（Stage 0）**——UUID/墓碑/rev/device_id/加密边界/UTC/导出可重入，现在多花几小时，Stage 5 少一次全量迁移；**③ LICENSE 与 `.gitignore`（Stage 0）**——确保本地数据和密钥**永远不进仓库**。测试上认清现实：后端+同步让测试面爆炸，单人覆盖不了，**只保 4 条关键路径自动化**（导出还原 / 同步冲突 / 数据隔离 / 加密不泄露），其余手工冒烟，并且**明确写下"哪些不测"**。开源意味着外部 issue/PR 与安全补丁，**请把"朋友只读优先、外部贡献以 issue 为主"写进你的维护策略**，否则单人带宽会被拖垮。

### 8.2 给「使用者」视角（宇日常使用时看这段）

**四个模块都会给你，热量也做完整版——但请接受一件事：它们不是同时成熟的。** 每个阶段你都会拿到一个"真的能用"的版本，先用起来、先形成习惯，再叠加下一层。之所以这样排，不是想少给你什么，而是因为**你不是缺第 4 个工具，你是被 3 个工具割裂了**——收口习惯没立住之前，堆模块只会让系统更重。热量完整版（粗记/半精/精记）我会照做，但**请你替自己守住一条底线：允许"只记一半"也算数**——研究反复证明"不完整但持续"胜过"完整但短暂"，**别为了记全而放弃**。还有一条请记住：**如果你哪天断了一周没打开，照样回来，不要判定自己失败**。范围扩大后最该被保护的功能其实是**随心记**——它天生就该被少用、被随手写、写完即沉底；它**不会因为你使用少而消失**，这是设计里唯一的例外。
