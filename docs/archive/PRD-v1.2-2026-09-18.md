## 📌 TL;DR（执行摘要）

宇的痛点是**「信息散在各处、来回切换、容易漏」**——这是信息架构问题，不是功能数量问题。因此首个交付版本的使命是：**建立一个能装下他全部事项、且「打开即知道今天干什么」的单一入口**。我们采用**统一事项模型 `Item`（形态/领域/跨度/状态四标签）+ 记录流 `Log` + 领域专属属性包**作为数据骨架，以**「今日视图」为唯一锚点**、以**「记一笔 ≤3 步 / ≤5 秒」为硬性验收线**。存储为 **SQLite 主存 + 显式一键导出**；导航为**「空间 Hub 折叠」**（一级仅 今日/收集/空间/复盘）。
**v1.2 更新（宇强制扩大范围）**：宇**否决"记录模块后置"**，**记账 / 热量 / 随心记 / 复盘四模块全部纳入首个交付版本**，热量并为**完整版**（但默认入口仍是粗记）；并新增**开源到 Git / 后端架构设计图 / Docker 一键运行**三项。团队**尊重该决定**，同时新增 **§8.5「范围扩大的代价与补偿机制」**：明确代价 + **模块级 14 天熔断** + **M0–M4 五阶段施工**（**M1 即首次可运行**，杜绝"全部做完才第一次跑"）。首版估算 **25–35 → 60–95 人日**。

## 1. 产品目标（3 个清晰、正交的目标）

> 三个目标互为约束、互不重叠：G1 管「收得进」，G2 管「看得见」，G3 管「带得走」。

**G1 · 收得进（Capture）**：任何想到的事、任何一条数值记录，都能在**≤3 步 / ≤5 秒**内进入系统，且**不需要用户做分类决策**。
—— 对应瑞思「发现 6」与数析 A1/「摩擦税」。这是所有功能的**前置条件**。

**G2 · 看得见（Consolidate）**：用户打开**一个地方**，就能看到「今天该干什么」以及各领域当下的状态；所有模块的产出都能被「今日视图 / 领域页」消化。
—— 对应瑞思「发现 1」。这是本产品**唯一成立的聚合理由**，也是与"再多一个 App"的分水岭。

**G3 · 带得走（Ownership）**：数据 100% 归属用户、离线完整可用、可一键免费导出为开放格式；**首个交付版本完全不碰账号与同步**。
—— 对应 D5 与竞析「数据主权」。这不是技术偏好，而是宇**信任这个系统的前提**。

**检验每个新需求的三问**（来自 G1–G3）：
1. 它如何被**今日视图**消化？
2. 它给**统一入口**增加了多少摩擦？
3. 它的数据能否**免费导出**、离线可用？

## 2. 用户故事（标准格式）

> 第一阶段 N=1（宇本人）；第二阶段朋友注册后追加，但首个交付版本不含。

**US-1（核心 · 收口）**
作为宇，我想要**在想记一件事时不用先想「这是待办还是笔记还是计划」**，只是把内容写下来，
以便**信息不再散落在备忘录、日历、Excel 三处**。
→ 验收：从「想到」到「条目入库」中位步数 ≤3、耗时 ≤5 秒；形态/领域/跨度由系统推断，可后改。

**US-2（核心 · 今日）**
作为宇，我想要**打开应用第一眼就看到今天该做的所有事**（今日待办 + 该打卡的习惯 + 到期的计划节点），
以便**不再靠脑子记「今天有没有漏」**。
→ 验收：今日视图一屏内可回答「今天做什么」，且跨领域聚合。

**US-3（领域 · 混装）**
作为宇，我想要**打开「健身」页就同时看到健身相关的打卡、待办和长期目标，并能分开记录力量训练与有氧**，
以便**这个页面不退化成一个通用待办清单，且力量与有氧的趋势互不混淆**。
→ 验收：健身页混装该领域全部内容；力量（动作/组/次/负重/休息）与有氧（时长/距离/配速/心率）**两套属性包可分别填写、分开看趋势**；不填也能作为普通记录保存。

**US-4（记录 · 低摩擦）**
作为宇，我想要**用同一套「记一笔」动作记涨跌（记账）、记吃练（热量）、记日记（随心记）**，
以便**不用为每类记录学一套新操作**。
→ 验收：三类记录共用统一入口与 Log 数据层；单条录入 记账 ≤20s / 热量 ≤30s。

**US-5（复盘 · 闭环）**
作为宇，我想要**在周末坐下来回看这一周，并把结论直接变回新的待办/计划**，
以便**复盘不只是报表，而是真的改变下一步**。
→ 验收：复盘结论可一键生成为 Item（带领域/跨度），进入今日视图。

**US-6（私密 · 随心记）**
作为宇，我想要**随手写的东西默认技术上不可能被任何人（包括将来的朋友、包括服务器）读到，且默认不进入任何聚合**，
以便**我敢写真的东西，而不是写给人看的**。
→ 验收：随心记条目本地加密存储；**默认不进任何统计/聚合/复盘**；无连续天数、无红点、无提醒。用户可**显式**允许"某一条"或"全局"进入复盘聚合——**默认值必须是隔离**。

**US-7（洞察 · 可复用语录卡片）**
作为宇，我想要**把「睡眠<6h 时待办延期率翻倍」这类跨模块结论以语录卡片形式出现在相关页面，且我能开关和改文案**，
以便**在需要的那一刻就看到洞察，而不是要专门打开复盘**。
→ 验收：Insight Card 为可复用组件，可出现在今日页/领域页/复盘页；用户可全局或逐卡开关、可编辑文案模板；卡片的数据依赖必须可用（否则不渲染）。

**US-8（交付 · 开源 / 可自部署）**
作为宇，我想要**把这个项目开源到 Git、附上架构设计图，并能在一台机器上用 Docker 一键跑起来**，
以便**我自己在飞牛 NAS 上部署，也让懂技术的朋友能复现与贡献**。
→ 验收：仓库含 LICENSE + README 结构 + `.env.example`（无硬编码密钥）；架构设计图并入技术架构文档；`docker compose up` 单命令可运行且数据卷持久化。

## 3. 用户研究洞察（来自瑞思 · 提炼）

> 证据分级沿用瑞思标签：**【事实】/【推断】/【外部佐证】/【判断】/【矛盾】**。
> 声明：以下引用**仅使用瑞思报告中未标注「无法溯源」的条目**；凡标注【无法溯源】的数字本 PRD 一律不作为论据。

| # | 洞察 | 对设计的直接含义 | 证据等级 |
|---|---|---|---|
| I1 | 痛点是**「检索与聚合」**不是「能力不足」——他从未说某工具功能弱 | 「今日视图」是唯一核心指标，不是汇总页 | 【事实】+【判断】 |
| I2 | 他的「7 个模块」混了**三种分类逻辑**（形态/领域/归属），自己没统一框架；D1 的四标签是**我们替他补的框架**，他第一眼会懵 | 界面**必须语义转译**；形态/跨度默认推断、可后改，**不作必填** | 【判断】 |
| I3 | 健身/学习是**唯一两个天然需要结构化记录**的领域；若统一 Item 只有标题+状态，健身页会退化成待办清单。**宇已验证：健身=力量 + 有氧，且要分开记** | D1 需补**领域专属属性包**（可选填）；健身领域需**力量/有氧两套** | 【事实·已验证】+ MyFitnessPal 官方/社区佐证 |
| I4 | 记账/热量/随心记是**同一件事的三次敲门**——都是「带数值的按时间记录」 | 抽象出统一 `Log`；不建三套表，而建**预设模板** | 【判断】 |
| I5 | 他要「随心记与复盘分开」，本质是**两个认知模式**分开。**宇已验证：随心记进复盘的可见性由用户可选** | **分交互、合数据**（方案 C）；**默认隔离 + 显式开启**（对方案 C 的细化） | 【事实·已验证】+【判断】 |
| I6 | 最高弃用风险是**录入摩擦随模块数线性增长** | 「记一笔中位步数 ≤3 / ≤5 秒」写进硬性验收 | 【判断】+ 强佐证（多来源重复的失败链条） |
| I7 | 复盘在他心里是**动作/输出物**，不是数据类型 | 复盘 = 读取层 + 生成层；**结论可回写为 Item** | 【判断】 |
| I8 | 他主动说「可能还有没想到的场景」——是**邀请也是责任** | 回给他**带吸附力排序**的场景清单，并明确说「哪些建议不做」 | 【事实】+【判断】 |
| I9 | 反馈循环风险：他既是需求方又是实现方，容易按「我能做什么」而非「我真用什么」设计 | 用**行为**（上周实际打开过哪个工具）而非**意愿**校准范围 | 【判断】 |

**两条被明确保留、不得单边消解的判断：**
- **【矛盾·必须同时呈现】**「all-in-one 必败」（主流评论）与「一本本子装下所有领域」的 BuJo 成功实践并存。**结论落在：问题不是「聚合 vs 分散」，而是「聚合的代价是否低于分散的代价」。**（详见 §6 设计考量的第四段）
- **【矛盾·必须同时呈现】** A 类「我想变好」型记录（体重/睡眠/喝水）弃用风险**高**；B 类「我怕出事」型（续费/人情/证件到期）弃用风险**低**——**B 类才是鲁棒需求**。故场景推进优先级为 **B4 → B1 → B2 → B3**，而非按「宇提到的顺序」。

**矩阵读出的三点**（竞析）：
1. **没有任何竞品同时具备「本地优先 + 自建部署 + 多模块生活聚合」**——这是宇的空位。
2. **「复盘」是普遍空位**：多数产品要么没有，要么只是统计报表。
3. 本项目的姿态是**「每一列都打勾，但不与任何单列的最强者比深度」**。

### 4.2 聚合边界的判断标准（可操作，非含糊）

一个模块**该聚合**，当且仅当**同时满足**以下 4 条（满足 2 条以下坚决外包）：

| # | 判据 | 反例（该外包） |
|---|---|---|
| 1 | **数据能被「今日/领域」视图复用** | 看剧进度、游戏存档 |
| 2 | **与已有模块共享同一次决策** | 「热量摄入」与「今日训练」同属健身闭环 → 聚合；「股票行情」→ 外包 |
| 3 | **录入能压缩到「一句话/一键」级别** | 复式记账、专业报税 |
| 4 | **深度可接受「够用」（80 分）而不追求「权威」（99 分）** | 医学级营养处方、企业财报 |

**用此标准检验宇的三个新模块**：记账 / 热量 / 日记**三者都通过** → 可以聚合。**但「通过检验 ≠ 塞进统一事项模型」**（见 §7 数据模型的矛盾调和）。

### 4.3 对标结论与「该外包的清单」

**该对标**：Super Productivity 的架构（本地优先 + BYO 同步 + 无账号可用）+ TickTick 的聚合克制（统一数据主干 + 环绕视图）+ flomo/小卡健康的录入范式 + Actual Budget 的数据主权。

**该外包 / 直接不做**：专业财务报税（→ 券商/财务软件）、医学级营养（→ 营养师）、深度知识管理（→ Obsidian）、团队协作（→ Notion）、**社交/社区/排行榜（直接不做，会扭曲个人记录行为）**。

**该警惕**：绝不设**付费墙**（TickTick「日历收费」引发最强反弹）；绝不**广告**（鲨鱼记账「记账 5 秒、关推荐 10 秒」）；导出**必须免费无锁**（随手记「账带不走」是第一触发点）。

## 5. 数据依据（来自数析 · 含单用户成功指标重定义）

> 数析证据分级：**A = 同行评审/权威一手；B = 行业报告；C = 厂商自述/内容营销（不作结论依据）；D = 其推断**。
> 本 PRD 只引用其 **A/B 级** 条目作为论据。

### 5.1 支撑「必须控范围」的证据（A/B 级）

| 证据 | 出处 | 对本项目的含义 |
|---|---|---|
| 21 功能 vs 7 功能播放器：购买时更受欢迎，**使用后满意度更低、复购意愿更弱** | Thompson et al., **feature fatigue**（MIT SMR 转述） | 「功能多」提升初始选择、伤害留存 |
| **80% 功能很少或从未被使用；12% 功能吃掉 80% 使用量** | Pendo 2019（615 个订阅产品） | 主导航必须极窄（≤5） |
| 人均**每天 3.5h / 7 个 App / 每月 26 个 App** | Sensor Tower《State of Mobile 2025》 | 「再装一个 App」的成本是挤进这 7 个名额 |

### 5.2 支撑「记录类功能是脆弱品类、必须降摩擦」的证据（A 级）

| 证据 | 出处 | 含义 |
|---|---|---|
| **「logins decreased sharply after the first month」，但满意度高** | Laing et al., *Annals of Internal Medicine*, 2014（N=212） | 塌方是行为本身撑不住，不是产品烂 |
| RCT 作者原话：每条记录「几分钟」，用户**「觉得太繁琐」** | 同上 | **放弃第一因是时间成本，不是意志力** |
| **到第 10 周只剩不到一半的人还在记录**；依从性**从第 3–5 周开始下降** | Hoover et al., *J Acad Nutr Diet*, 2019；*J Acad Nutr Diet*, 2015 | 试用期定为 **28 天**正好覆盖放弃悬崖 |
| 放弃六因子中「数据不准/无用」独立成因子，与永久放弃显著相关 | Attig & Franke, 2020（N=159） | 光记录不给价值 = 放弃 |
| 设预算组**查看频率上升，但支出零变化**；平均超支到自己目标的 1.3–1.4 倍 | Irrational Labs 2019 RCT（N=9,035） | **「看到数字」≠「改变行为」**——记账必须给「解释」不是「报表」 |
| 「我不喜欢写下来，因为看到实际花了多少让我很焦虑」 | JMIR Formative Research, 2023（定性） | 禁红/绿赤字框架，改用百分比/中性陈述 |
| 行为自动化中位 **66 天，18–254 天；错过一天对结果无显著影响** | Lally et al., 2010（N=96） | **禁止 streak 断一天清零**（该数字长期被误用） |
| 「每天至少记 2 顿」的天数，比「记录完整度」更能预测结果 | Patterson/Hoover et al., 2019 | **「不完整但持续」胜过「完整但短暂」**——模块必须允许只记一半 |

### 5.3 给单用户产品重新定义的成功指标（首个交付版本）

> **明确：不用 DAU / 留存率 / 转化率 / ARPU。** N=1 时分母为 1，N<20 时不具统计意义；且这些指标衡量「商业捕获」，与「信息收口 + 行为改变」的目标不一致（Irrational Labs 已证「高参与度可被焦虑刷高、且不带来改变」）。

**北极星**：**每周「未收口事项总量」持续下降并在低位稳定。**
**一级拆解（两个必须同时改善）**：
- **A. 系统外记录逃逸率（Capture Escape Rate）↓** —— 「信息是否还散着」的直接度量
- **B. 逾期未收口事项数（Overdue Open Loops）↓ 并稳定 ≤10** —— 「收口是否真的发生」

**关键指标表（阈值标 [估] 者需宇用 2 周基线实测校准）：**

| # | 指标 | 定义 | 健康阈值 |
|---|---|---|---|
| A1 | 单条捕获耗时 TtC | 「决定记录」→「条目可见」的秒数 | 移动 ≤10s / 桌面 ≤15s [估]；>30s 不合格 |
| A2 | **系统外逃逸率** | 本周新增中仍留在系统外（备忘录/微信/纸质/脑子）的比例 | **<20% 且不上升** [估]（北极星分量） |
| A4 | **逾期未收口数** | 已过原定时间但未终结（完成/明确放弃）的事项数 | **≤10 且 7 天滚动不增** [估]（北极星分量） |
| B1 | 主导航模块数 | 一级可见模块数 | **≤5** [估] |
| B3 | **僵尸模块数** | 连续 21 天零写入的模块数 | **= 0**（>0 必须降级） |
| B4 | 模块录入摩擦 | 单条记录耗时中位数 | 记账 ≤20s / 热量 ≤30s / 随心记无上限 [估] |
| B6 | 一句话测试 | 「这个模块回答了什么一句话问题？」 | **必须答得出** |
| C1 | 记录密度 | 过去 7 天有记录的天数 ÷7 | 总体 ≥5/7；单模块 ≥3/7 [估] |
| C2 | **宽容连续天数** | 连续记录，但允许 1 天缺口不清零 | 看「历史最长」而非「当前连续」 |
| C3 | 中断恢复率 | ≥2 天断连后 48h 内恢复记录的比例 | ≥80% [估] |
| C4 | 记录后使用率 | 记录条目后来被回看/引用的比例 | ≥30% [估] |
| D1 | 离线可用率 | 断网下核心动作成功率 | **100%**（Local-first 硬承诺） |
| D2 | 导出可还原性 | 每月「全量导出→空环境还原」数据完整率 | **100%** |

**实验方法（n-of-1 单被试设计）**：Week 0–2 录基线（只记录不改设计）→ Week 3–6 引入 **1 个变量** → Week 7 对照；目标指标改善 ≥20% 且无其他指标恶化则保留，否则回滚。**一次只改一个变量；改之前先写判据。**

## 6. 信息架构与导航

> 约束：**主导航模块数 ≤5**（数析 B1，依据 Pendo 12%/80% 法则）。
> 原则：**领域是主组织轴（D2）；形态是交互轴、不进导航（D3）；跨度是属性、不单独开页（D4）；界面必须语义转译（瑞思 发现 2）。**

**推荐导航结构（底部主导航 4 项 · v1.2 主理人裁定）：**

```
[ 今日 ]     [ 收集 ]     [ 空间 ]     [ 复盘 ]
   │            │            │            │
   │            │            │            └─ 周复盘 / 月复盘 / 自定义周期（读取层）
   │            │            └─ 空间 Hub：内含 健身 / 学习 / 工作 / 个人 四个 Tab
   │            │               （每个 Tab = 该领域「混装页」：打卡+待办+计划+记录+热量/记账）
   │            └─ 收集（Inbox）：未归类/未处理事项（统一捕获的落地点）
   └─ 今日视图：唯一锚点。跨领域聚合「今日该做的一切」+ Insight Card
        （设置 / 导出 / 备份 / 空间管理 / 模板管理 收在「今日」右上角，不占一级导航）
```

**关键设计规则：**
1. **导航形态已由主理人裁定：「空间（领域）Hub 折叠」**——一级只有「今日 / 收集 / 空间 / 复盘」**4 项**（比 ≤5 红线更紧）；健身/学习/工作/个人收在「空间」里，其内页为**混装页**（宇明确要求），顶部用 Tab 切换领域。这样既满足宇"健身页/学习页各自混装"的要求，又不让领域数直接撑爆导航。
2. **形态/跨度不出现在导航，也不出现在新建表单必填项**——用户看到的是「我要记一件健身的事」，系统内部才落到 `领域=健身`。
3. **空状态即引导**：新用户打开「今日」看到的是「写点什么」的输入框，而不是空白看板（对齐 flomo「打开即写」）。
4. **每日打开频次最高的动作必须 ≤2 次点击可达**（今日视图 → 记一笔）。
5. **热量/记账等记录模块不占一级导航**——它们从「空间」领域页内进入（混装），或经统一捕获入口直接记录。

> ✅ **导航形态已裁定（v1.2）**：采用「空间 Hub 折叠」。原开放问题 Q3 关闭。

## 7. 数据模型

> 设计原则：**统一的是「容器」与「记录流」，扩展的是「容器里的格式」与「预设模板」。** 所有表**预留同步字段**，但首个交付版本 **不启用同步逻辑**（D5）。
> **存储载体（v1.2 主理人裁定）**：**SQLite 作主存 + 内置一键导出**（全量 JSON + Markdown 文本镜像）。不选纯文本文件为主，理由是记录类数据量增大后检索与一致性会崩；SQLite 单库"被锁死"的风险用**显式一键导出**解决。**不做实时双写镜像**（会引入一致性与性能问题）——只做显式导出。
> ⚠️ **技术实现细节（后端设计图 / Docker / 存储引擎选型 / 同步协议）见技术架构设计文档**：`deliverables/product-strategy/tech-architecture-2026-09-18.md`（由架构师并行产出）。本 PRD 只定义产品级数据契约，不重复技术细节。

### 7.1 核心实体

**① `Item`（统一事项 · D1）**
| 字段 | 说明 |
|---|---|
| `id` | 主键（本地生成 UUID，避免多端冲突） |
| `title` / `body` | 标题 / 正文（随心记=纯 body） |
| `type`（形态） | `habit` 习惯 / `todo` 待办 / `plan` 计划 / `record` 记录（随心记，无状态流转）——**决定交互层** |
| `domain`（领域） | `fitness` / `study` / `work` / `life`（**可自定义增删**）——**决定归属空间** |
| `horizon`（跨度） | `short` 短期 / `long` 长期——**属性，不开页**（D4） |
| `status`（状态） | `inbox` 收件箱 / `todo` 待办 / `doing` 进行中 / `done` 完成 |
| `due_at` | 到期时间（可选） |
| `remind_at` | 提醒时间（可选；**首版仅"续费/到期"类允许提醒，随心记禁止**） |
| `payload`（**领域专属属性包**，可选 JSON） | **健身-力量**=`{exercise, sets, reps, weight, rest}`；**健身-有氧**=`{duration, distance, pace, avg_hr}`；学习=`{book, pages, duration}`。**不填也能记事，填了才有趋势**（瑞思 发现 3）。**力量与有氧为两套独立 payload schema，趋势分开渲染** |
| `is_private` | 随心记条目置 `true`，触发本地加密存储 |
| `review_visible` | **随心记专用**：`false`（默认）/`true`。**默认隔离**，用户须**显式**允许某条或全局进入复盘聚合；`false` 条目对复盘读取层不可见 |
| `created_at` / `updated_at` | 时间戳 |
| `sync_rev` / `device_id` / `is_deleted` / `sync_state` | **同步字段预留（首版不使用）** |

**② `Log`（记录流 · 主理人编排判断 #1，采纳）**
> **一笔「带数值的按时间记录」= `Log`。** 记账/热量摄入/热量消耗/习惯打卡/体重在**结构上是同一种东西**。**新增这类模块 = 新增「预设模板」，而不是新建三套数据表。**

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `log_type` | 判别字段：`habit_checkin` / `expense` / `calorie_in` / `calorie_out` / `weight` / … |
| `ts` | 发生/记录时间 |
| `value` | 数值 |
| `unit` | 单位（`count`/`min`/`CNY`/`kcal`/`kg`…） |
| `direction` | 方向（收支：`in`/`out`；热量：`intake`/`burn`）——可选 |
| `category` | 分类（记账=「项目」如 饮食/娱乐/数码/出行；**用户可自定义**） |
| `note` | 备注 |
| `item_id` | 关联的 Item（可选，如"跑步习惯"的打卡） |
| `domain` | 归属领域（供领域页与复盘聚合） |
| `created_at` / `updated_at` / `sync_rev` / `device_id` / `is_deleted` | 同步字段预留 |

**③ `Template`（预设模板）**：`{log_type, 默认 domain, 单位/方向约束, category 字典, payload_schema, 默认展示形态}`。
—— 「记账」「热量」「体重」「打卡」各自是一个模板实例；**这就是"新增模块而不新增数据表"的落地方式**。

**④ `Review`（复盘配置 · 非数据实体本身）**
> **复盘不是数据实体，而是「读取层 + 生成层」**（瑞思 发现 7）。它没有自己的内容表，只有配置与产出。
`ReviewConfig = {period: weekly|monthly|custom, cadence, remind_at}`；
`ReviewOutput` → **回写为新的 `Item`**（可带 domain/horizon）——**这是整个系统闭环的关键**。

**⑤ `InsightTemplate`（跨模块洞察卡片配置 · v1.1 新增）**
> 宇要求「语录可在相关页面直接展示，用户可选是否显示及自定义语录」。因此它是一个**可复用 UI 组件（Insight Card）**，而非复盘专属。
`InsightTemplate = {id, 触发规则(依赖的数据源/条件, 如 "睡眠<6h → 待办延期率"), 文案模板(可编辑), 展示位置(今日|领域|复盘), enabled(默认 true)}`；
**渲染前置条件**：卡片所依赖的数据源必须已存在且样本足够，否则**不渲染**（而非显示"无数据"）。
⚠️ **依赖缺口**：示例洞察依赖「睡眠」数据，而**睡眠（B6）当前不在首版/增强版范围内** → 首批可用卡片必须改用**已入库数据**（打卡率/待办延期/记账趋势/体重 vs 热量/力量 vs 有氧），睡眠类卡片需等 B6 上线。

### 7.2 【矛盾调和】统一事项模型 vs 三套独立数据模型

- **竞析主张**：「记账/热量/日记本质不同，必须是三套独立数据模型，绝不能塞进统一事项模型。」
- **瑞思/主理人主张**：数据层合并（Log 抽象），交互层分开。
- **本 PRD 的调和（可验收）**：**`Item` ≠ `Log`，两者是两条并行的主干。**
  - 「记账塞进 Item」确实是错的——**我们不这样干**；记账是 `Log(log_type=expense)`。
  - 但**记账/热量/体重/打卡在「时间戳+数值+单位」上高度同构**，用一张 `Log` + `log_type` 判别字段 + 类型化 `payload`/模板约束，既满足**逻辑上分开**（各自有模板、单位、方向、分类字典），又让**「复盘」能跨模块聚合**（这是本产品唯一护城河，瑞思 §6.4）。
  - **判据**：若未来某个 log_type 需要与其余类型**完全不同的事务语义**（如复式记账的双边分录），则**为它单开表**，而不是污染 `Log`。首个交付版本的记账**只要流水**，不需要。

### 7.3 同步字段预留说明
所有表**从第一天带上** `updated_at / sync_rev / device_id / is_deleted(tombstone) / sync_state`，但**首个交付版本不实现同步逻辑**（D5：完全不碰账号与同步）。目的是**避免第二阶段为加同步而"重写"**（反 Logseq「重写吃掉项目」教训，竞析 §3.4）。**数据结构宁可简单可迁移**。

## 8.5 范围扩大的代价与补偿机制（v1.2 新增）

> 宇**强制扩大了范围**（四个记录模块全部前移入首个交付版本），**我们尊重他的决定，但不假装没有代价**。本节诚实记录代价，并给出补偿机制。

### 8.5.1 明确牺牲了什么（代价清单）

| 代价维度 | 具体牺牲 | 受影响指标 |
|---|---|---|
| **交付周期** | 首个交付版本由约 25–35 人日 → **约 60–95 人日**（2–3 倍），首次可用时间显著推后 | 时间 |
| **测试覆盖深度** | 四类记录模块 + 开源 + Docker 并行，**单测/集成测试的边际覆盖被摊薄**；热量（食物库/分量）与复盘的聚合逻辑尤其难测 | D4 崩溃率、数据正确性 |
| **打磨度** | 每个模块可达"能用"，但**难以同时达到"专用 App 水准"**（瑞思 G3 条件 1：至少一个模块达专用水准）——聚合产品的护城河正建立在此 | 留存 |
| **边界场景处理** | 断网记录后回填、跨周期复盘、随心记加密与导出并存、时区/跨天打卡等边界**可能延后修** | 数据一致性 |
| **文档完整度** | 面向"朋友/开源使用者"的文档（README、部署、FAQ）会**落后于功能** | 开源可用性 |
| **学习曲线 / 维护带宽** | 单人维护 5–6 个模块（竞析"安全区上沿"），且开源后要接 issue/PR，**维护债上升**（反 Logseq 教训） | 长期可持续性 |

**一句话**：扩大范围买的不是"更多价值"，而是**"更晚拿到第一次的真实反馈"**——这正是瑞思「四段式死亡链」最危险的起点。

### 8.5.2 补偿机制（一）· 模块级熔断规则【新增】

> 每个记录模块（记账 / 热量 / 随心记 / 复盘）**上线后观察 14 天**，不达标即降级或移除。**规则必须先写、不许事后补**（G3）。阈值参考数析 §7.3 与瑞思 C1/C2/C3 约束。

| 判定 | 规则（任一满足即触发） | 动作 |
|---|---|---|
| ✅ **保留** | 14 天内记录密度 **≥3/7**（C1）且**回看 ≥2 次**（B5） | 转正，进入常规监控 |
| ⚠️ **观察（延长 7 天）** | 密度在 **1–2/7** 或回看 **1 次** | 延 7 天复评；**期间不得再加任何模块** |
| 🔻 **降级** | **连续 7 天记录密度 <1/7** | 从一级/领域页首屏移出 → 折叠进「更多」；**数据保留**；不弹提醒、不显示红点 |
| ⚫ **标记僵尸** | **连续 30 天零写入 且 零回看** | 标记 `zombie`，默认折叠；仪表盘 `Zombie Modules > 0` 报警（B3） |
| ❌ **移除** | **连续 60 天零写入** | 从导航移除（**数据保留 + 可一键恢复**）；若要再试须重走准入 |

**三条红线（模块级一票否决）：**
- **R1 · 摩擦税红线**：任一模块引入后，**核心指标（A1 TtC 或 A2 逃逸率）恶化 >20%** → **立即暂停该模块**，无论它自己表现多好。
- **R2 · 无赤字框架**：任何模块不得引入红/绿赤字框架（Irrational Labs + 负面情绪证据）。
- **R3 · 允许不完整**：任何模块不得强制完整性，"只记一半"也能保存并产生价值（Patterson/Hoover 2019）。
- **R4 · 并发上限**：**同时进行中的新模块 ≤1**（避免无法归因）。

**与瑞思约束的对应**：C1（锚点唯一=今日）→ 防"多锚点"；C2（摩擦守恒，新增模块不得增加统一入口步数）→ 与红线 R1 一致；C3（任一模块连续 4 周零使用应降权而非删除）→ 与「降级」动作一致（**降权不删数据**）。

### 8.5.3 补偿机制（二）· 施工顺序与阶段验收点

> **核心原则：「四个模块都要」≠「四个模块一起做完才能第一次跑」。** 分阶段交付，**M1 结束即首次可运行**，避免"全部做完才第一次运行"这种最危险的做法。

```

   ├─ Log 数据层 + 习惯打卡（P0-7）

   ├─ 领域属性包（力量+有氧）（P0-12）
```

### B. 坚决否掉（即使宇想要，也建议不做 + 理由）

| # | 建议否掉 | 理由（证据） |
|---|---|---|
| **X1** | **「漏了就断」的 streak 视觉表达 / 红点催促** | Lally 2010（A 级）：**错过一天对结果无显著影响**，硬 streak 恰与原文矛盾、且把「偶发断连」升级为「弃用」；Attig & Franke 2020：断连是正常现象。**改为「历史最长 + 本月 21/28 天」的累积型指标。** |
| **X2** | **把「随心记」与「复盘」合并成一个编辑框** | Stone/JMIR 证据：被观测会扭曲记录真实性；合并**同时毁掉两者**（瑞思 §4.4、方案 B 为最差选择）。**改为方案 C：分交互、合数据。** |
| **X3** | **把「记账」塞进统一事项模型（Item）** | 记账本质是「带数值的时间记录」，塞进 Item 会让"复盘的跨模块聚合"失真；**应走 `Log`（其本质是 竞析"独立数据模型"与主理人"Log 抽象"的调和，见 §7.2）。** |
| **X4** | **要求每一笔记录都填完整（强制分类/强制精确到克/强制写全）** | Patterson/Hoover 2019（A 级）：**"不完整但持续"胜过"完整但短暂"**；强制完整性直接抬高摩擦 → 触发死亡链。**改为 R3：任何模块允许"只记一半"也能保存并产生价值。** |
| **X5** | **红/绿赤字框架（预算超支变红、卡路里超标变红）** | Irrational Labs RCT + JMIR 定性：赤字框架反复触发内疚 → 放弃。**改为百分比进度 / 趋势方向 / 中性陈述。** |

## 14. 成功指标（首个交付版本 · 单用户阶段）

> **明确：不用 DAU / 留存率 / 转化率 / ARPU。** N=1 时分母为 1；且这些指标衡量"商业捕获"而非"信息收口 + 行为改变"。

**北极星**：**每周「未收口事项总量」持续下降并在低位稳定。**

**一级分量（必须同时改善）**：
1. **系统外记录逃逸率 <20% 且不上升**（A2）——"信息是否还散着"
2. **逾期未收口事项数 ≤10 且 7 天滚动不增**（A4）——"收口是否真的发生"

**过程指标（首版期间监控）**：
- 单条捕获耗时 TtC：移动 ≤10s / 桌面 ≤15s（A1）
- 主导航模块数 ≤5（B1）
- 僵尸模块数 = 0（B3）
- 离线可用率 = 100%、导出可还原性 = 100%（D1/D2）
- 记录密度：总体 ≥5/7（C1）
- 中断恢复率 ≥80%（C3）

**方法**：n-of-1 单被试实验——**Week 0–2 录基线 → Week 3–6 引入 1 个变量 → Week 7 对照**；改善 ≥20% 且无其他指标恶化则保留，否则回滚并记录在案。**一次只改一个变量；改之前先写判据。**

> ⚠️ **阈值纪律**：所有标 [估] 的阈值**无公开基准**，须用宇的 **2 周基线实测校准**后才能作为硬指标。**不得把他人的商业 App 大盘留存数字外推为本产品的 KPI。**
