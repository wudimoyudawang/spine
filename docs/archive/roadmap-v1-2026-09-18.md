## 📌 TL;DR（3-5 行）

1. **v0.1 只做一件事：把「统一收集 + 今日视图」跑通并验证 21 天，零记录模块。** 宇自选的范围就是这两个，路线图的第一条纪律是**不加东西**。
2. **四个新模块全部不进 v0.1。** 进入 Next 的顺序是 **复盘 V0 → 随心记 → 记账极简**；**热量单独押后到 Later，且只以「28 天实验」而非「功能」形式存在**。我同意瑞思：**复盘必须排在数值记录之前上线**——它是所有记录类功能的存活条件。
3. **v0.1 的技术重心不在功能，而在"为第二阶段同步预留"：** 客户端 UUID、墓碑软删除 + 每条 `rev`、`device_id`/`owner_id` 占位、随心记条目级加密边界、UTC 时间戳、含同步字段的导出 schema。**这些现在不做，将来一定要重写（Logseq 教训）。**
4. **砍掉的比加入的多。** 最坚决的一条：**拒绝「漏了就断」的 streak 强惩罚与红点催促**。它看起来"合理"、宇最可能主动要，但证据一致地反对它。
5. 没有可靠的时间估算依据，故**全部用 Now / Next / Later，工作量用 S/M/L/XL**，不编具体日期。

## 1. 排序框架与口径调整说明

### 1.1 我替换了「业务价值」的口径

| 原口径 | 替换后 | 理由 |
|---|---|---|
| 业务价值（收入 / 获客 / LTV / 付费转化） | **用户留存价值** —— 该项对「宇在 30 天后是否还在用」的贡献度 | **①** 目标用户是**单用户自建部署，没有收入与获客**，原口径在 N=1 时恒等于 0，无法区分任何两个需求（数析 §6.0：「分母为 1」）。**②** feature fatigue 研究（Thompson et al., 2005，A 级）证明「吸引选择的功能」与「留住使用的功能」是**两组不同的功能**——对单用户产品，**留存才是唯一的生死线**。**③** 与北极星（未收口事项下降）保持同向，避免出现「指标好看但事情没变」的翻版（数析 §4.2 Irrational Labs RCT）。 |

> **口径声明**：本路线图**不采用任何商业留存/转化 KPI**。任何外部 App 的大盘留存数字（如 D30 8%–12%）**仅用于标定量级，不作为本产品 KPI**（数析 §8「不可外推原则」）。

### 1.2 五维权重与评分方向

| 因素 | 权重 | 评分方向（1–5 分） |
|------|------|---------|
| 用户影响 | 30% | 5 = 影响场景最多、痛点最严重 |
| **用户留存价值** | 25% | 5 = 直接决定「还回不回来」；1 = 与留存无因果 |
| 战略对齐 | 20% | 5 = 高度契合 D1–D5，**尤其「减少信息分散」+「能被今日视图吸收」** |
| 工程成本 | 15% | **5 = 成本最低/最易实现**（反向，S 级≈5，XL 级≈1） |
| 依赖风险 | 10% | **5 = 依赖最少/风险最低**（反向） |

**总分 = (0.30×影响 + 0.25×留存 + 0.20×战略 + 0.15×成本 + 0.10×依赖) × 20**，取值 0–100。
**成本/依赖两列取"友好度"方向**，是为了让加权求和单调可比——**分值越高越好**。已在列头标注。

### 1.3 工作量口径

以「单人全栈开发（宇本人或等价 1 名工程师）」计，**1 人日 = 1 个专注工作日**。
**S ≤1 人日 ｜ M 2–4 人日 ｜ L 5–10 人日 ｜ XL >10 人日**。

## 4. v0.1 必须为同步预留的技术决策 ⭐（重点章节）

> **一句话结论**：v0.1 **不实现任何同步逻辑**（D5），但**必须现在就把"多端合并所需的最小数据契约"定死**——否则第二阶段要改动全部已存数据，重演「Logseq 重写吃掉项目」（竞析 §3.4）。**这份数据契约只占 v0.1 很小的工作量，却是整条路线图里最不可回溯的决定。**

### 4.1 必须在 v0.1 定死的 7 项

| # | 技术决策 | 为什么必须现在定 | 若不定会怎样（代价） | 推荐方案 |
|---|---|---|---|---|
| **T1** | **ID 生成方式** | 第二阶段是**多设备离线创建再合并** | 用自增整型主键 → 两台设备各自生成 `id=1,2,3…` → **必然冲突**，合并时被迫全量重编 ID（等于重写） | **客户端生成 UUIDv7**（时间有序、索引友好、可排序）。**禁止自增整型。** T1 是七项里最便宜、也最不可回溯的一项 |
| **T2** | **软删除 + 墓碑** | 删除必须可同步 | 硬删除 → 离线设备回连时**把已删记录复活**（"僵尸数据复活"） | 所有表加 `is_deleted` + `deleted_at`；**禁硬删**。删除=打墓碑 |
| **T3** | **每记录版本 / 时钟** | 需要可判定的冲突解决依据；**设备时钟会漂移** | 仅靠 `updated_at` 做 LWW，会因时钟偏差误判新旧 | 每条记录带 **`rev`（单调版本号）+ `updated_at`（UTC）**，冲突解决用 **`rev` 优先、`updated_at` 兜底**（简单可迁移的 LWW，**不引入 CRDT**） |
| **T4** | **`device_id` / `owner_id` 占位** | 冲突归因 + 第二阶段多用户 | 后补字段要做 schema 迁移；权限模型无处挂载 | 所有表带 `device_id`；带 `owner_id`（v0.1 恒为本地单用户常量）。**成本极低，是给第二阶段的"保险"** |
| **T5** | **随心记的加密边界** ⭐ | 若 v0.1 明文存、第二阶段才改 E2EE，**要全量重加密迁移**；且"朋友可见"世界要求它**架构级不可读**（瑞思 §2.3） | 迁移时若加密方案变更 → 历史条目无法解密/泄露；导出/备份可能夹带明文 | **条目级密文存储**：`is_private=true` 的条目只存**密文 + nonce**，带 `enc_version` 字段以便算法演进；**密钥不与数据同存**；**导出/备份默认排除明文**（除非用户显式选择）。加密边界**按条目**而非整库，才与将来的 E2EE 同步兼容 |
| **T6** | **时间统一 UTC（+ 可选时区）** | 跨设备、跨时区显示一致 | 存本地时间 → 换设备/改时区后时间错乱，且不可逆 | 统一存 **UTC**（epoch）；如需展示本地时间，另存 `tz`。**`Log.ts`（事件发生）与 `created_at`（记录系统）分离** |
| **T7** | **导出 schema 含同步字段 + 可重入** | 导出可还原 = 100% 是硬指标（D2），也是"数据主权"的信任根基 | 导出缺 `id`/`updated_at`/`device_id` → 重导入无法对上，还原率 <100% | 导出（JSON/CSV/Markdown）**必须包含 T1–T4 字段**；导入必须幂等（同一 `id` 重复导入不产生重复行） |

> **统一要求**：T1–T7 **不仅要落在 `Item` 上，还要落在 `Log`、`Template` 上**。PRD §7.3 已写「所有表从第一天带上同步字段」——本路线图把这句落成**可验收的 7 项清单**。

### 4.2 可以（也应该）推迟的项

| 推迟项 | 为什么可以推迟 |
|---|---|
| **实际同步协议 / 传输方式**（HTTP API vs WebDAV vs 自建） | 数据契约（§4.1）不变，传输方式随时可换 |
| **CRDT / 协同引擎（Yjs、Automerge）** | **v0.1 坚决不引入**——它是"过早的深度"，与「数据结构宁可简单可迁移」冲突。T3 的 LWW 足以覆盖"单人为主的个人工具" |
| **账号体系 / 鉴权 / 多用户权限模型** | D5 + N1/N2：第一阶段 N=1，过早引入会拖垮单人维护带宽。**T4 的 `owner_id` 占位已足够** |
| **服务端存储 schema / 同步 API 契约** | 第二阶段再定；客户端数据结构已稳定 |
| **冲突解决 UI** | 第二阶段；先保证"冲突可人工解决"即可 |
| **加密封装的最终算法 / 密钥派生细节** | 可先在 v0.1 做本地加密；**但 T5 的"边界与字段"必须现在定** |

### 4.3 v0.1 就要跑的验证法（把"不重写"变成可验收）

> **导出 → 空环境 → 还原 → 双端模拟合并**（在 v0.1 就跑，而不是等到第二阶段）：

1. 导出全量数据 → 在**空环境**还原 → 校验**数据完整率 = 100%**（对应 D2 指标）。
2. **模拟双端**：拷一份数据当"设备 B"，在 A、B 上各改同一条记录 + 各删一条 → 按 T1–T3 规则合并 → **验证无 ID 冲突、无删除复活、冲突可判定**。
3. **随心记加密验证**：确认备份/导出文件中**不含随心记明文**。

**通过标准**：以上三步全过，才认为"同步预留"有效。**这是本路线图里唯一一条"技术防重写"的硬验收。**

### 4.4 存储引擎与"数据可带走"的调和（一个必须现在拍板的取舍）

| 选项 | 优点 | 风险 |
|---|---|---|
| **纯开放文本文件**（Markdown/CSV） | 完全符合「数据永远是你能直接读的普通文件」（竞析 §3.4 的信任根基） | 结构化查询（今日视图聚合、跨模块复盘）实现麻烦、易慢 |
| **SQLite 单文件** | 事务、索引、聚合查询天然适合「事项 + 数值」混合 | 二进制格式，违背"人可直读"直觉；格式若变更=数据锁死风险 |

**推荐**：**SQLite 为主 + 持续维护一份开放文本镜像导出**（JSON+CSV+Markdown），并保证任意时刻都能从文本镜像完整还原。**这样既不牺牲聚合性能，又守住"数据永远带得走"的信任承诺**——这正是反 Logseq「2.0 变成 SQLite、不再能被外部编辑器手改」教训的落地方式。

> **待宇拍板**：是否接受「SQLite 主存 + 开放文本镜像」这一组合。若宇坚持纯文件主存，则 §4.1 的字段设计不变，但需接受查询复杂度的上升。

## 6. 模块扩展的判定规则

> **来源**：数析 §7.2/§7.3 的 G1/G2/G3 + 判定规则，融合瑞思 §6.3 的 C1/C2/C3 约束。
> **原则**：**加模块不是增长手段，而是风险动作**——必须用"闸门 + 熔断"管理，而不是"先做上去看看"。

### 6.1 加之前：先观察到什么信号？

**① 习惯已形成闸门（G1，全部满足且连续 21 天）**
- 核心捕获密度 ≥5/7（捕获零日 ≤2/周）
- 系统外逃逸率 **<20% 且趋势不上升**
- 逾期未收口数 **≤10 且 7 天滚动不增**
- 单条捕获耗时达标（移动 ≤10s / 桌面 ≤15s）

**② 摩擦预算闸门（G2，引入前静态评估）**
- 新模块单条录入 **≤30s**
- **不增加核心捕获路径的步数**（不能把"记一条事项"从 2 步变 4 步）
- 引入后**主导航仍 ≤5**
- 通过「**一句话测试**」：写下"这个模块回答的一句话问题"并归档（答不出=装饰）

**③ 熔断规则先写（G3）**
- **引入前**就写下"保留/降级/砍掉"的判定条件与试用期，**不能事后补**

**④ 瑞思的三条约束（与 G1–G3 并列生效）**
- **C1 锚点唯一性**：**不得**引入第二个承担"每日打开"责任的模块——今日视图是且仅是唯一锚点
- **C2 摩擦守恒**：新增模块**不得**抬高统一入口的平均操作步数
- **C3 活跃度门限**：任一模块连续 4 周零使用 → **降权（移出导航）而非删除**

**⑤ 并发约束**：**同时进行中的新模块 ≤1 个**（否则无法归因，也避免决策点爆炸）。

### 6.2 加之后：用什么指标判断保留还是降级？

**试用期 = 28 天**（理由：反复出现的放弃悬崖在**第 2–5 周**——Cordeiro「2 周 −50%」、Burke「第 3–5 周开始降」、Laing「第 1 月后塌方」、NCBI「第 10 周剩不到一半」。**28 天正好覆盖最关键那道坎**）。

| 判定 | 规则（任一满足即触发） | 动作 |
|---|---|---|
| ✅ **保留** | 第 3–4 周记录密度 ≥3/7 **且** 28 天内回看 ≥4 次 | 转正，进入常规监控 |
| ⚠️ **观察（延长 14 天）** | 第 3–4 周密度在 2/7 边缘，或回看 1–3 次 | 延长 14 天复评；**期间不得再加任何模块** |
| 🔻 **降级** | 连续 14 天记录密度 <2/7 | 从主导航移出 → 折叠进「更多」；**数据保留**；不弹提醒、不显示红点 |
| ⚫ **标记僵尸** | 连续 30 天零写入**且**零回看 | 标记 `zombie`，默认折叠；仪表盘 `Zombie > 0` 报警 |
| ❌ **移除** | 连续 60 天零写入 | 从导航移除（**数据保留 + 可一键恢复**）；想再试须**重新走 G1/G2** |

**四条模块级一票否决红线：**
- **R1**：引入某模块后，核心指标（TtC 或逃逸率）**恶化 >20%** → **立即回滚**（这是"摩擦税"红线，无论该模块自己表现多好）
- **R2**：**任何模块不得引入红/绿赤字框架**（只允许百分比 / 趋势方向 / 中性陈述）
- **R3**：**任何模块不得强制完整性**（必须允许"只记一半"也能保存并产生价值）
- **R4**：**同时进行中的新模块 ≤1 个**

### 6.3 n-of-1 自我实验法（单用户的"实验"怎么做）

```
Week 0–2   基线期：只记录，不改设计。采集全部指标。
Week 3–6   干预期：引入 1 个变量（如"记账模块"或"把捕获入口下沉到锁屏"）。
Week 7      对照：干预期 vs 基线期。
判据：     目标指标改善 ≥20% 且无其他指标恶化 → 保留；
           否则回滚，记录在案（"试过了，不行"也是有价值的知识）。
纪律：     一次只改一个变量（=R4）；改之前先写判据（=G3）。
```

## 7. 单用户阶段自检清单（可定期执行）

> **来源**：瑞思 §6.4-C「预言式弃用信号」+ 数析 §6.2 指标全表。**转成一张可定期执行的检查表。**
> **目的**：**出现任一红项 → 立即收缩范围，而不是加功能。**

### 7.1 每周自检（约 5 分钟，周日复盘时顺带完成）

| # | 检查项 | 健康标准 | 触发时的动作 |
|---|---|---|---|
| W1 | 统一入口**中位操作步数** | ≤3（**>5 为红**） | 红：停止加模块，先降摩擦 |
| W2 | 是否出现「**攒着晚上一起补**」行为 | 无 | 红：这是所有记录的死亡前兆，立即检查摩擦 |
| W3 | **任一模块**本周是否零打开 | 无 | 连续 2 周零打开 → 进入观察 |
| W4 | **系统外逃逸率**（本周新增中仍留在系统外的比例） | **<20% 且不上升** | 上升：捕获入口或推断有问题 |
| W5 | **逾期未收口数** | **≤10 且 7 天滚动不增** | 超标：今日视图/提醒机制失效 |
| W6 | 本周**捕获零日** | ≤2 天/周 | 超标：核心习惯未形成，**冻结一切新模块** |
| W7 | 记录**总体密度** | ≥5/7 | 未达：先回到核心，不加模块 |

### 7.2 每月自检（约 30 分钟）

| # | 检查项 | 健康标准 | 触发时的动作 |
|---|---|---|---|
| M1 | **问出「这个功能在哪儿？」的次数** | **累计 ≤3 次**（>3 为红） | 红：导航层承载不住，D3/D4 抽象失效 → 立即收缩 |
| M2 | **僵尸模块数**（连续 21–30 天零写入） | **= 0**（>0 必须降级） | 执行 §6.2 的「降级/标记僵尸」动作 |
| M3 | **中断恢复率**（≥2 天断连后 48h 内恢复） | ≥80% | 未达：宽容机制/回访设计有问题 |
| M4 | **记录后使用率**（记录条目后来被回看/引用） | ≥30% | 未达：**该模块只记不用 = 无价值**，考虑加复盘解释或降级 |
| M5 | **主导航模块数** | ≤5 | 超标：立即折叠，不得再增 |
| M6 | **离线可用率** | **= 100%** | 未达：Local-first 硬承诺被破坏，最高优先级修复 |
| M7 | **导出可还原性**（全量导出 → 空环境还原） | **= 100%** | 未达：数据主权风险，最高优先级 |
| M8 | **记录密度按模块** | 单模块 ≥3/7 为"在坚持" | 连续 14 天 <2/7 → 降级 |

### 7.3 每季度自检（约 1 小时）

| # | 检查项 | 触发时的动作 |
|---|---|---|
| Q1 | **模块数是否 >6？** | 冻结，回到 5–6；任何新需求先过 §6.1 闸门 |
| Q2 | **领域数是否 >5？** | 冻结领域，合并低频领域 |
| Q3 | **"必要"与"想要"的比例**：本月新增的模块里，有几个是"想要"（非真实触发事件驱动）？ | 超过半数 → 下季度禁止新增 |
| Q4 | **数据是否仍能一键免费带走？** | 若导出被任何门槛挡住 → 立即修复（这是第一触发弃用点） |

> **一句话原则**：**红色项出现时，收缩范围；不要用"再加一个功能"去解决"系统已经太重"的问题。**

## 8. 利益相关者沟通要点

> 受众就是**宇本人**——他既是产品负责人，也是开发者。因此针对**两种视角**各写一段。

### 8.1 给「开发者」视角（宇写代码时看这段）

我们的第一版**不追求功能，追求"不用重写"**。请把 v0.1 的工作重心分成两半：一半是把「统一收集 + 今日视图」跑通；**另一半——也是更值钱的一半——是把 §4.1 的 7 项数据契约定死**：客户端 UUIDv7、墓碑软删除、每条 `rev`、`device_id`/`owner_id` 占位、随心记的**条目级加密边界**、UTC 时间戳、含同步字段的导出 schema。**这些现在多花一点点力气，第二阶段就少一次全量迁移**——Logseq 用 13 个月的重写把项目拖进 ICU，我们不重复。同时请守住三条工程纪律：**① 同步逻辑一行都不写，但字段一个都不能少；② 不引入 CRDT（过早的深度）；③ v0.1 就跑通「导出→空环境→还原→双端模拟合并」三步验收**。最后记住 R1 红线：**任何新模块若让你的核心指标变差超过 20%，不管它多酷，立刻回滚。**

### 8.2 给「使用者」视角（宇日常使用时看这段）

你会觉得 v0.1 很小——**这是故意的**。你的痛点从来不是"少一个功能"，而是"被三个工具割裂、来回切换、容易漏"。所以第一版只做一件事：**让"想到什么就记下来"变成肌肉记忆，让"打开就看到今天该干什么"成为习惯。** 在你连续 21 天真正用它捕获、且系统外不再散着信息之前，我们**不加任何记录模块**——包括你想要的记账、热量、随心记。这不是拒绝，是**顺序**：先形成捕获习惯，再往上加载。等核心稳了，我们会按"最便宜建立信任"的顺序给你兑现三样东西：**体重闭环（你记了热量却没有结果反馈）、续费提醒（把一个抽象痛点变成每月都在发生的具体事件）、跨模块语录卡片（"睡眠<6h 的日子待办延期率翻倍"这类话，只有这个 App 说得出）**。热量一定会做，但它会以**"28 天实验"**而不是"正式功能"的形式出现——因为它是放弃最狠的品类，我们必须先验证你撑得过第 3–5 周那道坎。最后一句：**如果你哪天断了一周没打开，请照样回来，不要因此判定自己失败**——我们的设计里，"漏了"不等于"完了"。
