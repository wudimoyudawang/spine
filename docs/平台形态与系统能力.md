# 平台形态与系统能力边界

**日期**：2026-09-18
**回答的问题**：手机端要不要做 App、怎么做？PC 端用什么方式跑？

> 结论先给：**两端都从 PWA 起步；PC 端很可能永远不需要真 App；
> 手机端只在两个特定条件下才值得做成真 App，而且其中一个条件会被你自己的后端化解掉。**

---

## 1. 一条决定性的架构原则

各平台能力差异**很大**，而且会一直变。应对方式不是选一个「最好的平台」，而是：

> **把平台差异关进一个适配层，让业务逻辑对平台无感。**

具体到本项目，只需要两层：

| 适配层 | 隔离什么 | 为什么必须有 |
|---|---|---|
| `StorageAdapter` | 存储实现（IndexedDB / SQLite / 远端 API） | iOS 上浏览器存储可能被系统回收，将来要把本地存储换成 SQLite 时，只应改这一层 |
| `Capability` | 平台能力（全局热键 / 通知 / 分享入口 / 相机） | 同一个功能在浏览器、PWA、真 App 里的可用性完全不同，需要运行时探测 + 优雅降级 |

**第 1 步就要把 `StorageAdapter` 留出来。** 这是这份文档里唯一一条「现在不做、以后会很贵」的事。

## 2. PC 端 —— 已决定不做（2026-09-20）

这一节原来写的是三件事：桌面端推荐走浏览器 + PWA、「浏览器做不到系统级全局热键」、
以及要造桌面壳的话选 Tauri 而不是 Electron。**这些分析现在全部作废。**

作废的原因不是技术问题，是范围问题：

> 宇在 2026-09-20 明确：**这个项目只做手机端。**
> 而在此之前已经真做出来过一版 Windows 桌面版（Tauri 2 薄壳 + 便携版 exe + JSON 落盘，
> 同一份页面），也按这句话**整个删掉了** —— 删掉的只是外壳，页面本身一行没少。

只剩两条通用经验，将来换任何壳仍然成立：

- **页面和壳要分开。** 桌面版当时的做法是「exe 只是执行器，页面和数据都在它旁边」，
  改界面、改数据格式都不用重新打包。这条对手机壳同样适用。
- **别提前造壳。** 桌面版是在「点一下图标 + 输入 = 2 步，已经落在预算内」的情况下做的，
  属于把想象出来的需求提前落地。手机壳同理：先把 PWA 用起来，让摩擦自己暴露出来。

## 3. 手机端

### 3.1 先看 Android 和 iOS 的差距

这不是「细节差异」，是**可用性等级不同**：

| 能力 | Android (Chrome) | iOS (Safari) |
|---|---|---|
| 安装方式 | 自动弹出安装提示 | **无提示**，必须手动「分享 → 添加到主屏幕」 |
| Web Push 通知 | 支持 | 支持，但 **iOS 16.4+ 且必须先添加到主屏**，权限要从装好的应用里请求 |
| 后台同步（Background Sync） | 支持 | **不支持**，且 Apple 未公布计划 |
| 周期后台同步 | 支持 | **不支持** |
| 后台抓取（Background Fetch） | 支持 | **不支持** |
| 存储上限 | 较高 | 较低（约 50MB 量级） |
| 存储被系统回收的风险 | 低 | **存在**（详见 3.2） |
| Web Bluetooth / NFC / USB / 通用传感器 | 支持（Chromium） | **不支持** |
| 主屏小组件（widget） | 有 | **无**（PWA 没有 widget） |
| 应用图标长按快捷菜单 | 支持 | **不支持** |
| 真全屏 | 支持 | 不支持（状态栏常驻） |
| 浏览器引擎 | 可选 | **全部是 WebKit**（App Store 审核指南 2.5.6），装 Chrome 也一样 |

**一句话**：Android 上 PWA 是完全可信的主通道；iOS 上 PWA 是「能用、但有真实代价」的通道。

> **数据可靠性说明**：上表基于 2026 年 9 月的公开资料检索。
> 检索中发现**一处来源矛盾**：某篇 2026 年的文章称「iOS 17.4 在欧盟移除了独立 PWA 支持、
> 欧盟 PWA 只能在 Safari 标签打开且无 push」。另外三篇（含引用 Apple 官方文档的）
> 都说 Apple 在 17.4 正式版发布前**收回了这个计划**，欧盟用户的 PWA 与 push 至今可用。
> **我采信后者**（多源一致 + 有 Apple 官方材料支撑），但如果你或朋友在欧盟，
> 建议自行实测确认一次。

### 3.2 iOS 存储风险：这是本项目唯一必须严肃对待的平台问题

**事实**（WebKit 存储策略，多源一致）：

- Safari 对**普通浏览**的 script-writable storage（含 IndexedDB、localStorage、Cache API）
  有**7 天不使用即清理**的策略。
- **添加到主屏的 PWA 不受这条 7 天规则约束** —— WebKit 官方澄清过，主屏应用有自己的
  基于使用频率的计数器。
- **但配额仍然存在（约 50MB 量级），且存储压力下仍可能被系统驱逐。**

**这对本项目的含义**：你的架构原则是「本地存储是主体、云端是可选」。
在 iOS 上，这条原则**部分不成立** —— 本地副本可能被系统清掉。

**我的判断，以及为什么这不该改变你的架构**：

这个问题会被**你自己的后端**解决，而且正好是第 5 步要做的事。
第 5 步之后，云端不是「别人的服务器」，是**你自己的 NAS**。
那时 iOS 本地存储被清掉就只是「下次打开要重新拉一遍」，而不是数据丢失。

所以：

> **第 5 步不只是「给朋友用」，它同时是「手机端变可靠」的前提。**

在此之前（第 1–4 步），iOS 上必须有一条**手动兜底**：
一键导出全量 JSON，存到 iCloud Drive / 文件 App 里。这条导出功能本来就在计划里（防数据锁死），
在 iOS 上它有第二重身份。

**另外可以试但不保证**：调 `navigator.storage.persist()` 申请持久存储。
Chrome/Edge 桌面通常会给（基于站点参与度判断）；Safari 的支持情况与效果**需实测确认，我不敢断言**。

### 3.3 手机端的三条路线

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. PWA**（推荐起点） | 添加到主屏 | 零打包、零签名、零审核、即时更新、两端同一套代码 | iOS 上的全部限制（见 3.1）；存储可能被回收 |
| **B. Capacitor 打包**（需要时才做） | 同一份 React 代码 → Android APK + iOS App | 代码不用重写；能拿 QQ 原生能力；可用真 SQLite 插件解决存储问题；可上架也可自己装 | 需要签名流程；iOS 自签有 7 天有效期问题（见 3.4）；每次改动要重新打包 |
| C. React Native / Expo | 重写 UI 层 | 原生体验最好 | **要重写整个界面**。一个人的项目里这是纯粹的浪费 |
| D. Flutter | 重写 | 同上 | 同上，还要再学一门 Dart |

**C 和 D 直接排除**：它们意味着把已经定稿的界面结构重做一遍，收益只是「体验好一点」。
你的界面是列表、表单、卡片、图表 —— 这类界面在 Web 里已经足够好。

### 3.4 一个必须先知道的现实：iOS 自己装 App 很麻烦

这条会直接影响你的决策，所以单独说：

| 方式 | 有效期 | 成本 |
|---|---|---|
| 免费 Apple ID 自签 | **7 天**，过期 App 打不开，要重新签 | 免费，但要反复折腾 |
| 付费开发者账号自签 | 1 年 | 99 美元/年 |
| TestFlight | 90 天一轮 | 免费，但要走流程 |
| AltStore 等侧载工具 | 需电脑/特殊配置，也是 7 天 | 免费，折腾 |

**所以在 iOS 上，「做成真 App 自己用」本身就是一个持续的负担**，
而 PWA 是**唯一零摩擦的路径**。

### 3.5 那么什么时候才值得做真 App

只有两个条件之一成立时：

1. **需要硬件能力**：蓝牙（如心率带、体脂秤）、NFC、后台定位、传感器。
   → 这些在 iOS 的 PWA 里**无解**，只能真 App。
   → 但对本项目，**先问「不做行不行」**：体重可以手输、运动数据可以从手环 App 同步后手抄一条。
2. **本地存储必须绝对可靠**。
   → **这条会被你自己的 NAS 后端化解**（见 3.2）。

**如果真要做了，用 Capacitor**：React 代码一行不改，加 `@capacitor-community/sqlite`
就能拿到真正的 SQLite，彻底解决存储可靠性。

## 4. 推荐路径（按时间顺序）

只列手机端。PC 那一列已经删掉了，见第 2 节。

| 阶段 | 手机端 | 触发条件 |
|---|---|---|
| 第 1 步 | 浏览器 + 添加到主屏 | — |
| 第 2–4 步 | Android：添加主屏就能用<br>iOS：添加主屏 + 定期导出兜底 | — |
| 第 5 步 | 存储风险由自建后端化解 | 后端 + 同步做完 |
| 之后 | 如果确认需要蓝牙等硬件能力 → **Capacitor** 打真 App | **真实痛点出现时**，不提前做 |

**核心原则**：**不提前造壳。** 先在没有壳的情况下用够久，让壳要解决的问题自己暴露出来。
