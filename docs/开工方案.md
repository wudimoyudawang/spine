## 2. 技术栈（一个方案，不再列候选对比）

选型只服从一个原则：**你一个人维护，越少的心智负担越好。**

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | **React + TypeScript + Vite**，Tailwind，PWA | 生态最大，AI 辅助写代码最顺；一套代码覆盖手机和电脑，手机「加到主屏」就接近原生 |
| 客户端存储 | **IndexedDB（Dexie）** | 浏览器里最稳的本地库。离线完整可用就靠它 |
| 前后端共享 | **Pydantic model（唯一事实来源）→ FastAPI 自带 OpenAPI → `openapi-typescript` 生成前端 TS 类型** | 类型仍然只写一遍，但只写 Python 那一遍。生成物是产物，不要手改 |
| 后端 | **Python 3.12+ / FastAPI + Pydantic v2 + SQLModel** | ★ **已修正（原为 Node + Fastify）**。你主语言是 Python，且要学 agent —— Pydantic 就是 Function Calling 的 schema 来源，FastAPI 就是 MCP Server 的宿主。理由与代价见《与两个 Agent 项目的技术协同》 |
| 数据库 | **SQLite（SQLModel / SQLAlchemy 2.x）** | 单文件、零运维、事务安全。你和小范围朋友这个量级，SQLite 完全够，不需要 PostgreSQL |
| 向量检索 | **sqlite-vec 扩展**（和主库同一个 `.db` 文件） | 将来做「随心记语义检索」用。零额外部署 —— **不要为练手引入 Milvus 容器**，那会让 NAS 部署变复杂 |
| 部署 | **Docker Compose，单容器** | FastAPI 同时托管前端静态文件和 API，就一个服务一个卷，最简单。镜像约 200MB（Node 约 60MB），自用无所谓 |
| HTTPS | **Caddy 容器**或 NAS 自带反代 | 内网穿透暴露公网时必须有 HTTPS，Caddy 能自动签证书 |

> ⚠️ **一个必须提前知道的坑**：SQLite 文件**不要放在 NAS 的 SMB/NFS 网络挂载目录上**（飞牛的存储空间要注意这一点），网络文件系统上的文件锁不可靠，会导致数据库损坏。把它放在容器可访问的**本地盘路径**，或者用 NAS 上非网络挂载的路径。

## 3. 数据模型（这份文档里最重要的部分）

好在这个模型定对了，后面加功能基本不用改结构。全部表共享一组**同步预留字段**：

```sql
-- 每张同步表都带这一组，v1 不用，但必须建
id          TEXT PRIMARY KEY,      -- UUIDv7，客户端生成（禁止自增整型）
created_at  INTEGER NOT NULL,      -- UTC 毫秒
updated_at  INTEGER NOT NULL,
deleted_at  INTEGER,               -- 墓碑软删除，永不物理删除
rev         INTEGER NOT NULL DEFAULT 1,
device_id   TEXT,                  -- v1 留空
owner_id    TEXT                   -- v1 留空
```

### 3.1 `item` —— 事项（习惯 / 待办 / 计划）

```
type        TEXT   -- habit | todo | plan   ← 决定交互（打卡 / 勾选 / 进度）
domain_id   TEXT   -- 归属领域                    ← 决定出现在哪个空间
horizon     TEXT   -- short | long               ← 只是属性，不单独开页面
status      TEXT   -- inbox | todo | doing | done | archived
title, note
due_at, start_at, end_at
progress    INTEGER  -- 0-100，计划用
repeat_rule TEXT     -- JSON，习惯的重复规则
payload     TEXT     -- JSON，★领域专属属性包
```

**`payload` 是关键**。它给「事项」挂结构化细节，**不用为每个领域建表**。这样做的好处：加一个新领域 = 加一条数据，不是加一次改表。

```jsonc
// 一次训练事项（要练什么、几组几次）—— 注意这是「计划要做什么」
{ "kind": "strength", "exercises": [{ "name": "深蹲", "sets": [{"weight": 80, "reps": 5}] }] }
// 一次有氧事项
{ "kind": "cardio", "mode": "跑步", "plan_km": 8 }
// 一个学习事项
{ "kind": "study", "book": "…", "target_pages": 30 }
```

> **别把它和 `log` 搞混**（这是最容易混的一处）：
> - `item.payload` = **打算做什么**（计划），有状态、会完成、能被勾掉。
> - `log` = **实际发生了什么**（记录），没有状态、不会完成、只增不改。
>
> 「今天要练腿」是 `item`；「今天深蹲 80kg × 5×5」是 `log`。两个都要有 —— 只记计划就不知道做没做，只记结果就不知道本来想干什么。
>
> 而且从第 3 步起，**记录这件事由「记录项」（`record_type`）定义，不再由 `payload` 里的写死结构负责** —— 见 §3.4.2。`payload` 只留给「事项本身」需要结构化的时候。

### 3.2 `log` —— 记录流（记账 / 习惯打卡 / 全部领域记录项，都是这一张表）

这是整个设计里最省事的一招：**记账、习惯打卡、热量摄入、热量消耗、体重、领域里的自定义记录项，结构上是同一种东西** —— 按时间发生的一条记录。所以只用一张表，靠 `kind` 区分，靠「记录项定义」给用户不同的输入界面。

```
kind        TEXT   -- money | habit_tick | <record_type.id>
record_type_id TEXT   -- 指向 record_type；记账与习惯打卡为 NULL
occurred_at INTEGER
value       REAL      -- 数值型记录填这里（可为 NULL）
unit        TEXT      -- 元 / kcal / kg / 次 / 分钟 / 分 / 页
text        TEXT      -- ★纯文字型记录填这里（可为 NULL）
category_id TEXT      -- 记账分类 / 食物分类
item_id     TEXT      -- 关联的事项（可选）
payload     TEXT      -- JSON，比如记账的收支方向、食物的份量
```

> **`value` 和 `text` 允许都为空、允许只有一个、也允许都有。** 这一条决定了「纯文字记录」和「数值记录」不需要两张表 —— 你现在写的「今天练了什么」和「深蹲 80kg」，在库里是同一张表的相邻两行。

> **`kind` 里没有 `weight`、也没有 `calorie_in`。** 这是本轮的一个修正：热量摄入、热量消耗、体重**不是内置类型，而是健身领域下面的三条记录项** —— 和「深蹲最大重量」「模拟考试分数」地位完全相同。所以它们走 `record_type_id`，不占内置枚举。
>
> 直接后果：将来你想加「喝水」「睡眠时长」「阅读页数」，**都不用改表结构，加个记录项就行**。这才是「记账/热量/日记不是三个新功能」的真正落地方式 —— 如果给每个新想法都加一个内置 `kind`，这张枚举迟早会变成一坨没人敢动的历史包袱。

### 3.3 `note` —— 随心记（唯一需要加密的表）

```
content_cipher  BLOB   -- 加密后的正文
nonce           BLOB
enc_version     INTEGER
day_key         TEXT   -- 归到哪一天（每日一篇用）
review_visible  INTEGER DEFAULT 0   -- ★默认 0：不进任何统计与复盘
```

**`review_visible` 默认必须是 0。** 你自己也选了「用户可选是否出现」——默认隔离、显式开启。原因不是隐私洁癖：只要写的时候知道它会被拿去汇总审视，人就会开始修饰叙事。默认关掉，随心记才能是真的随心记。

`created_at` / `updated_at` **不加密**（同步要用），只有正文加密，密钥单独存、不进导出文件。

### 3.4 其余表

| 表 | 用途 | 关键字段 |
|---|---|---|
| `domain` | 领域（健身/学习/工作/个人，可增删改名） | name, icon, sort, **pinned** |
| `record_type` | **领域里的自定义记录项** | domain_id, name, mode(text\|number), unit, **quick**, sort |
| `category` | 记账分类 | name, icon, direction(income\|expense) |
| `food_preset` | 常吃项（半精记复用） | name, kcal, unit |
| `capture_rule` | **自动判断规则（用户可写）** | match_kind(kw\|re), pattern, exclude, target, enabled, sort |
| `review` | 复盘 | period, range_start, range_end |
| `insight` | 语录卡片 | template(JSON), params(JSON), scope, enabled |
| `user` / `device` / `sync_cursor` | 第二阶段用 | — |

分类图标就是这个：`category.icon` 存一个图标名，前端渲染。**不是逐条记录配图**，所以没有附件存储和同步体积的问题。

`record_type.quick` 决定这条记录项**要不要出现在首页快记的类目里**（见 §3.6.2）。`capture_rule` 是**唯一一张由用户写入判断逻辑的表**，它必须跟着数据一起导出 —— 规则写错了可以改，但规则丢了你会不知道刚才那句话为什么被记错。

### 3.4.1 领域是用户自己长的，不是写死的四个

**每个领域天然就有三样东西：待办、习惯、长期目标。** 结构完全一样，变的只是名字和你填进去的内容。这是本方案的骨架之一 —— 所以「考证」「育儿」「副业」这类领域，你自己点一下就能建，不需要改代码、更不需要等谁给你加。

| 能力 | 说明 | 实现成本 |
|---|---|---|
| 新建领域 | 输入名字即建，自动带上空的待办/习惯/长期目标三个容器 | 约 20 行代码 |
| 改名 | 直接改 `domain.name` | 零成本 |
| 删除 | **只删入口，不删内容** —— 里面的东西回到收件箱等重新归类 | 软删除，零成本 |
| 置顶到顶部快捷 | `domain.pinned = 1`，左上角出现一键入口 | 一个布尔字段 |
| 领域专属记录项 | 存 `record_type` + `log` 两张表（**不是** `item.payload`） | 见 §3.4.2 |

**领域专属记录项是可选的增强，不是建领域的前提。** 健身里有热量摄入/热量消耗/体重/力量训练/有氧，学习里有书目页数，其他领域暂时什么都不填 —— 空的领域照样能用，它只是「待办 + 习惯 + 长期目标」。

> **别把两件事混起来**：`item.payload` 回答「我**打算**做什么」（硬拉目标 100kg、每周 30 页），`log` 回答「我**实际**做了什么」（今天硬拉 90kg × 3、读了 24 页）。两个都要有 —— 只有前者是愿望，只有后者是流水，而复盘要看的恰恰是这两者的差距。

**顶部快捷区就是 `pinned` 这一列的筛选视图**，不是一个新概念、不是新表、不是新页面。所以「哪些领域在顶部」永远和你自己的置顶操作一致，不会出现两处配置对不上的情况。

**为什么删除只删入口**：领域是一种分类，而分类一定会有你分错的时候。如果删领域会连带删掉里面的记录，你以后就不敢删、也不敢建新领域了 —— 那这个「自定义」就是假的。分类可以错，数据不该丢。

### 3.4.2 领域里的「记录项」也是自定义的，只有两种方式

这是 3.4.1 的下半句。领域建好之后，**它里面记什么，也是你自己定** —— 不是我给你预设「健身只能记力量和有氧」。

一个记录项就四个字段：**名称、方式、单位、要不要出现在首页快记**。方式只有两种：

| 方式 | 适合 | 输入界面 | 列表怎么显示 |
|---|---|---|---|
| **纯文字** `text` | 过程和感受：今天练了什么、错在哪、这本书讲了什么 | 一个文本框 | 日期 + 文字 |
| **数值** `number` | 趋势和对比：热量摄入、体重、深蹲最大重量、模拟考试分数 | 一个数字框 + 单位 | 日期 + 数字，外加一行「最近 / 上次 / 增量」 |

举几个只有你自己会想到的例子：考证领域建「模拟考试分数」（数值 · 分）和「错题复盘」（纯文字）；育儿领域建「身高体重」（数值 · cm/kg）和「今天说了什么新词」（纯文字）。**健身领域里预置了热量摄入、热量消耗、体重这三条** —— 它们是记录项，不是内置功能。

**为什么只给这两种，而不是让你自己设计表单字段**：字段一多，录入就慢，录入一慢这个功能就死了（记账和热量记录的死法都是这个）。两种方式覆盖了「记录过程」和「观察趋势」这两件真正需要的事，再往上加字段只会让人写不动。真需要更多细节时，纯文字记录里随便写。

**删除语义与领域一致**：移除记录项只是从界面收起来，**已经记下的内容仍在库里和导出文件里**。所以你不会因为「当初建错了名字」而失去任何数据。

> 技术上的关键：`log.value` 和 `log.text` 允许一个为空。所以「纯文字」和「数值」**共用一张记录表**，不需要两套结构 —— 这也是为什么它和记账、热量、体重能活在同一个体系里，而不是旁边再挂一个子系统。

### 3.5 索引

「今日视图」是最高频查询，必须建好索引，否则记录一多就卡：

```sql
CREATE INDEX idx_item_today  ON item(status, due_at) WHERE deleted_at IS NULL;
CREATE INDEX idx_item_domain ON item(domain_id, status) WHERE deleted_at IS NULL;
CREATE INDEX idx_log_time    ON log(occurred_at) WHERE deleted_at IS NULL;
CREATE INDEX idx_note_day    ON note(day_key) WHERE deleted_at IS NULL;
```

### 3.6 信息架构：导航是从数据里长出来的

左侧固定五项，加一个由 `domain.pinned` 决定的快捷区：

| 入口 | 职责 |
|---|---|
| **今日** | 跨领域聚合：逾期置顶 → 今天到期 → 今天该打卡的 → 长期目标进度 |
| **收集** | 全局速记框 + 收件箱，只解决「先记下来别丢」 |
| **随心记** | 零字段文本框，无统计、无红点、无连续天数 |
| **空间** | 两层：领域（健身/学习/工作/个人 + 你新建的）+ 记账。**热量和体重不在这里** —— 它们是健身领域里的记录项 |
| **复盘** | 周 / 月 / 自定义周期 |
| 顶部快捷（动态） | 你置顶的领域，一键直达 |

**关键点：这个列表的长度不随功能增长。** 上面五项是固定的，下面那段动态区完全由你自己勾。所以「入口越加越多、最后找不到东西」这个最常见的退化方式，在这套结构里不会发生。

领域页内部永远是同一套排布：**习惯 → 待办 → 长期目标 → 记录项 → 领域设置**。这就是「混装」的落地方式 —— 你点进「健身」，看到的是这个领域里所有的事，不需要在页面之间跳。

> **关于「热量放哪儿」这个决定**：空间页原来有三个并列入口（记账 / 热量 / 体重），现在只剩**记账**一个。理由不是记账更重要，而是**记账是唯一一个真的需要独立页面的** —— 它有收支方向、分类统计、按项目看，不只是记个数字。而热量、体重就是「带单位的数字」，它们和「深蹲最大重量」「模拟考试分数」没有任何结构区别，硬给它们一级入口，等于承认「记录项」这个抽象不成立。

### 3.6.1 首页只留一个输入框

首页顶部是**一个**输入框，不是一排功能按钮。这是整份方案里最影响日常手感的一处设计。

**旧做法（已被替换）**：速记框存收件箱 + 三个「记一笔支出 / 记热量 / 记体重」按钮。问题是按钮**点了要跳到记账页** —— 记一笔小事要换页、找位置、填表、再回来。这条路径每多一步，你少记的概率就大一截。

**现在的做法**：写一句话，按规则判断它是什么，回车就存，**不跳页、不填表**。

| 你写的 | 它会记成 |
|---|---|
| `32 午餐` | 支出 ¥32 · 分类「餐饮」 |
| `¥32 午餐` | 一样 |
| `1800 kcal` | 健身 → 热量摄入 1800 kcal |
| `71.4 kg` | 健身 → 体重 71.4 kg |
| `深蹲 80kg × 5 × 5` | 健身 → 力量训练（纯文字记录） |
| `写周报` | 待办 · 进「今天」 |
| 认不出来的任何东西 | 收件箱，先存着 |

**四条必须遵守的规则**（原型里已经这样做了，也有测试覆盖）：

1. **认不出来不许丢。** 认不出就进收件箱 —— 宁可多一步归类，不能丢。
2. **更不许瞎猜。** `交物业费 200` **不会**被记成 200 元支出（数字不在开头就不当金额）；`5 公里` 不会被当成 5 元。**目标是数值记录项、但这句里没有数字时，也会放弃这条规则**，而不是硬塞一个 0 进去。这一条比第一条更重要：丢一条你还能补，记错一笔你要过很久才发现。
3. **判断错了要能一眼看见并改掉。** 输入框下面实时显示「会记成：支出 ¥32 · 餐饮 · 命中『数字在开头 → 记一笔支出』」，旁边一句「不对就点上面的类目」—— 类目 chips 永远在，手动点一次就**完全跳过**自动判断。
4. **任何页面按 `/`（或 Ctrl+K）都能直接开始记。** 不在首页就先跳回首页并高亮输入框，不需要「先导航到对的页面」。

**这一版不是 AI，是一个规则引擎。** 但规则不是写死在代码里的常量 —— 见下一节。真正「读懂一句话」仍然不在本轮范围；将来接上模型时，**输入框和流程一行不用改**，换掉的只是引擎内部。

> 顺便一个免费的收敛：原来首页有「速记框 + 三个记录按钮」两个入口，容易犹豫「这该写哪」。现在只有一个，犹豫成本归零。**记完的东西立刻在下面「今天记下的」里出现** —— 看得见才有正反馈。

### 3.6.2 「记一笔」的两处自定义：哪些类目出现 + 判断逻辑由你写

这是本方案里**唯一一处允许用户写判断逻辑的地方**，所以单独说清楚。入口在**首页速记框右侧的 ⚙**，就地在首页展开，不跳页 —— 因为你调整它的时机，通常正好是要记东西的那一刻。

#### （一）出现哪些类目，你勾

输入框下面那排 chips，来源有两处：

| 来源 | 说明 |
|---|---|
| **系统行为项** | 自动判断 / 待办 / 随心记 / 记一笔支出 / 只丢进收件箱。可关。但**「自动判断」关不掉** —— 它不是类目，是「我不指定」的默认态；关掉它，你每次都得手动选。 |
| **你的记录项** | `record_type.quick = 1` 的全部记录项，**自动**出现在这里。在领域页新建一条记录项（比如「喝水量」），它立刻进 chips，不需要谁给你开权限。 |

**这里有一个刻意的区分：类目顺序不可调，规则顺序可调。**
理由很实在 —— 类目顺序只影响你好不好找，**不影响记对记错**；而规则顺序**直接决定结果**（先命中先用，取第一条）。只把「会影响正确性」的东西做成可调的，免得你面对一堆没必要调的排序按钮。

#### （二）自动判断的逻辑，你来写

规则表就是这个项目的识别引擎。每条规则四件事：

```
匹配什么  →  用什么方式匹配（关键词 / 正则）
         →  排除什么（可选）
         →  判成哪个类目（支出 / 待办 / 随心记 / 收件箱 / 任意一条记录项）
```

原型里预置了四条：一条是**你自己的示例**（`深蹲／硬拉／卧推 → 力量训练`），三条是内置规则（带卡路里 → 热量摄入、带公斤 → 体重、数字在开头 → 支出）。

**三条设计原则，都不是可选项：**

1. **你自己的规则永远排在内置规则前面。** 你写的应该压过我的默认判断。所以「上移／下移」**不允许跨到内置组里去** —— 这是刻意的限制，不是没做完。新加的规则插在你那组的最前面，保证它第一句就生效，不会被旧规则先抢走。
2. **必须有实时测试框。** 输入一句样例，立刻显示「会记成什么」+「命中了哪条」+「其他每一条为什么没命中」。**没有这个框，这个功能就是坏的** —— 用户写完规则不知道对不对，等于没写。
3. **只给关键词和正则，不给脚本。** 理由见 §9。

**已知风险（写在这里，不能等踩到再说）：**

- **正则灾难性回溯（ReDoS）**：用户写出 `(a+)+` 这类嵌套量词，可能让整个页面假死。
  - 现状：原型里有一道**挡板**（嵌套量词 + 超长直接拒绝保存），并有测试。
  - 真实实现必须加固：`pattern` 长度上限、拒绝嵌套量词、**把匹配放进 Web Worker 并设超时**。JS 的正则**没有内置超时机制** —— 这一条不做，一次笔误就是一次页面卡死。
- **规则冲突没有真值可依**：两条规则都想命中一句话时，唯一的裁判是「谁在上面」。所以测试框必须逐条列出命中情况，让顺序问题可诊断，而不是让用户靠猜。

## 4. 后端设计

### 4.1 API

第一阶段（**不实现，但先把形状定死**，免得将来推倒重来）：

```
POST /api/auth/register     -- 小范围分享：改成邀请码注册，不开放自助注册
POST /api/auth/login        -- → access token + refresh cookie
POST /api/auth/refresh
POST /api/auth/logout
GET  /api/sync/pull?since=<cursor>   -- 增量拉取
POST /api/sync/push                  -- 提交本地变更
GET  /api/health                     -- Docker healthcheck 用
GET  /                               -- 前端静态文件
```

### 4.2 鉴权

自建，不引第三方：

- 密码用 **argon2id** 存哈希
- access token：短期 JWT（15 分钟），放内存
- refresh token：httpOnly + Secure + SameSite=Lax 的 Cookie（30 天）
- `ALLOW_REGISTRATION=false` 为默认值，开放注册用邀请码

### 4.3 同步（第二阶段实现）

不做 CRDT，不做实时协同。就四步：

1. 客户端保存 `last_cursor`
2. `push`：把本地 `rev`/`updated_at` 有变化的行发上去
3. 服务端逐行比较 `updated_at`，**后写胜出**；有冲突的行**不覆盖，另存一份副本**（`conflict_` 前缀），事后你自己决定留哪个 —— 宁可留垃圾，不要丢数据
4. `pull`：返回 `seq > cursor` 的行

**首次登录时本地已有数据的处理**（这是最容易丢数据的地方，你之前也问过）：给三个选项 —— `用本地覆盖云端` / `用云端覆盖本地` / `合并`，默认选**合并**，并且**合并前自动导出一份本地备份**。

services:

personal-hub/

用 **pnpm workspace** 做 monorepo —— 一个人管得过来，且 `packages/shared` 能被两端直接引用。

**LICENSE 建议 AGPL-3.0。** 关键差别就一句：MIT 允许别人拿你的代码改成闭源服务卖钱且不回馈；AGPL 要求「谁把它当网络服务跑，谁就得开源自己的改动」。你做的是自建自用的本地优先工具，这正是你会在意的场景。如果你完全不在意，MIT 最省事。

**CI（GitHub Actions）**：lint + typecheck + test，打 tag 时构建镜像推到 GHCR。

**开源前必做的一件事**：确认 `.gitignore` 覆盖了 `.env`、`*.sqlite`、`data/`。密钥或数据库误入库是一票否决级事故 —— 而且一旦推上去，history 里永久留着。

## 7. 施工顺序（5 步，每步结束都能真的用起来）

不是七个阶段，没有验收委员会。**原则只有一条：每步做完，你都能真的打开它、用它记一件事。**

| 步 | 目标 | 做完后你能干什么 | 顺路的 AI 练习点（都可跳过） |
|---|---|---|---|
| **1** | 能记下来 | 仓库骨架 + 类型定义 + IndexedDB + **一个速记框（内置规则识别 + 类目 chips + `/` 唤起 + 「今天记下的」反馈）**。跑起来，随手写一句话就能存住并落对地方 | — |
| **2** | 把结构交给你 | **⚙ 自定义面板（类目开关 + 你自己写规则 + 实时测试框）** + 今日视图 + 领域 Hub（今日/收集/空间/复盘）+ 三种交互（打卡/勾选/进度条）+ 领域可自定义（新建/改名/删除/置顶）+ 记录项可自定义（纯文字 / 数值） | **① 结构化输出**：把速记框的规则识别换成模型调用 |
| **3** | 能记住细节 | 记账（流水 + 分类图标 + 按项目看）+ 随心记（零字段）+ 一键导出全量 JSON | — |
| **4** | 能回头看看 | 复盘（自动汇总 + 结论回写成新事项）+ 健身的预设记录项（热量摄入 / 热量消耗 / 体重）+ 语录卡片 | **② 向量检索**：随心记搜索<br>**④ 单 Agent**：复盘配文 |
| **5** | 能给朋友用 | Docker 打包 + 后端 + 邀请码账号 + 增量同步 + 开源发布 | **③ MCP Server**：后端做好后顺手封一层 |

> 「健身力量 / 有氧分开」不再是写死的属性包 —— 它现在是第 2 步里你自己建的两个记录项（`力量训练` 纯文字 + `深蹲最大重量` 数值）。**这样你将来想要别的领域也能自己加，而不是等谁给你加。**

> **为什么「规则可写」放在第 2 步、而速记框在第 1 步**：第 1 步先用内置三条规则把「写一句话就能记对地方」跑通，你立刻能用；等你知道自己实际会怎么写、被哪句话绊住，再打开规则编辑器 —— 那时候你知道自己要什么规则。反过来先做编辑器，你会对着一个空表单不知道写什么。

> 练习点的作用、边界与学习顺序见《与两个 Agent 项目的技术协同》。**核心规则只有一条：AI 只能长在增强层，核心层的写入路径一行 LLM 调用都不许有。**


第 5 步之前的所有步骤，**你都不用碰服务器**。这很重要：如果你先做后端，会在没有任何真实使用数据的情况下设计同步协议 —— 那是这个项目里最贵的错误。

## 8. 验收标准（就两条）

别的一律是参考，这两条做不到，做多少功能都没用：

1. **记一笔 ≤ 3 步 / ≤ 5 秒**（自己拿手机掐表，从解锁到存下）
2. **连续两周每天都打开过它**

第 2 条不达标时，**不要加新功能，先把摩擦找出来**。

### 三个月规则（替代之前那套熔断阈值表）

某个模块连续三个月没被打开过 → 从导航里收起来，**数据保留不删**，想用再放出来。

就这一条。原因：你是自己用的工具，不需要「降级/冷却期/僵尸判定」这套流程，你只需要一个不挡路的收纳抽屉。

| 语录卡片的文案模板 | 同上，先做 2–3 条试试 |
| 手机推送提醒 | iOS 对 PWA 通知限制很大，不承诺。先用「打开即见今日」 |
| **规则引擎要不要支持脚本** | **本轮明确不做**，写在这里是为了说清理由，不是留个待办。允许执行你写的 JS 有三个问题：① 安全 —— 这个项目要开源、要给朋友注册，一条被导入的规则就可能变成恶意代码；② 不可解释 —— 脚本只给结果，不告诉你哪条命中了；③ 导出不安全 —— 规则要跟着数据走，脚本会把一件本来安全的事变危险。关键词 + 正则覆盖绝大多数真实需求，真不够用时再单独讨论，**但不在 v1 里为它预留接口**。 |
| 正则 ReDoS 的真实加固 | 原型里只有一道简易挡板（嵌套量词 + 超长拒绝）。真实实现必须补：`pattern` 上限、嵌套量词检测、**匹配放进 Web Worker 加超时**（JS 正则没有内置超时）。这一条属于「上线前必须做」，不是优化项 —— 用户一次笔误就是一次页面假死。 |
